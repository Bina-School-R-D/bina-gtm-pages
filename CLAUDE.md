## 🔴 TOP RULE — reply in short bullets, never a wall of text

- **Short bullets only.** No paragraphs, no prose blocks, no endless analysis. Outranks everything else here.
- **Show an example, don't explain.** Proposing a page? Give the section list + the 5 headline numbers — not an essay about the narrative.
- **Ceiling:** ~10 bullets normally, ~15 for a page-strategy answer. Over that, cut.
- **Tables beat bullets** for stat lists, page inventories, and option comparisons — use them.
- **Always end with:** actions I'll take + decisions I need from you. If neither, say "no action needed."

## Stack

- Astro 6 + Tailwind CSS v4 (static output). Same stack as thebinaschool.com and headerpath-website.
- Hosted on **GitHub Pages**. `.github/workflows/deploy.yml` builds and deploys on every push to `main`.
- `public/CNAME` pins the custom domain — never delete it.
- **Tracking is a mirror of thebinaschool.com, set in `BaseLayout`** — GTM container `GTM-M2HWS5K` (CookieYes CMP + GA4 live inside it), PostHog, and `public/attribution.js`, a port of the main site's file. **PostHog is the one deliberate exception to parity**: it sends to a dedicated project for this domain — `go.bina.school`, us.posthog.com project `578193`, key `phc_D4SE…` — with session replay + console-log + performance capture enabled server-side, so this domain's traffic and replays are watched separately from the main site's project (`phc_u3t5…`). **PostHog also loads eagerly** (async, not deferred — Akis, 2026-08-26) so every visit gets a replay, including sub-5s bounces; GTM and attribution.js keep the main site's deferred loader (after load + 5s, or first interaction). All three are host-gated to `*.thebinaschool.com` / `*.bina.school`, so local dev and previews stay out of the numbers. Re-extract from the live site if the main site's stack changes — don't invent a second setup.
- **Attribution contract:** `attribution.js` stores the *first* `utm_*` / `gclid` / `ref` set it sees (localStorage, 365 days) and appends it to every `form.thebinaschool.com` link, both on load and again in the click capture phase. `localStorage` is per-origin, so a first touch captured on go.bina.school is only carried across by those URL params — which is why the params, not a cookie, are the mechanism. Partner links that must attribute through go.bina.school still need `?ref=` on the go.bina.school URL itself.

## 🔴 Color & accent usage

Applies whenever a page/section uses the dark palette (page bg `#1c1c1c`, card bg `#000000`, tokens `--color-dark-bg`/`--color-dark-surface`/`--color-dark-border` in `global.css`). Approved accent colors and their contrast ratios (both already ≥4.5:1 WCAG AA):

| Accent | Class | Hex | On `#1c1c1c` | On `#000000` |
|---|---|---|---|---|
| Grass (teal) | `bina-grass` | `#03ecc5` | 11.2:1 | 13.8:1 |
| Yellow | `bina-yellow` | `#f7d928` | 12.1:1 | 14.9:1 — fill/pill only, never text (see brand rule below) |
| Purple | `bina-purple` | `#b38cff` | 6.6:1 | 8.1:1 |
| Pink | `bina-pink` | `#fe48c2` | 5.6:1 | 6.9:1 |
| Green | `bina-green` | `#03cb5b` | 7.9:1 | 9.7:1 |
| Blue | `bina-blue` | `#33afff` | 7.1:1 | 8.7:1 |
| Red | `bina-red` | `#ff605b` | 5.7:1 | 7.1:1 |
| Orange | `bina-orange` | `#fe6c23` | 6.0:1 | 7.4:1 |

- **Rule 1 — never white on dark.** Text sitting directly on `#1c1c1c` page bg or a `#000000` card always takes one of the 8 accents above — never `#FFFFFF`.
  - **`pill_source.astro`'s rating value (e.g. "5.0", "9.42/10") is `#E2CCFF` (lila), never white.** It used to render at `#e8e8e5` (near-white) by default and literal `#ffffff` on hover — both real Rule 1 violations, caught by contrast against the pill's platform-name text, which correctly stays `--color-muted-gray` (`#999999`, Rule 16) throughout, including on hover. The lila-vs-muted-gray contrast is what makes the rating value stand out from the platform name next to it — that's the pill's whole visual hierarchy; white was never necessary for it.
- **Rule 2 — always black on an accent card.** When the card itself is filled solid with an accent (e.g. a `bina-grass` card), its text is `#000000` — never white, never a different accent. **Never a faded/opacity-reduced black either** (e.g. `text-coal-900` `#313131`, or unstyled text that falls through to `body`'s own default `text-coal-1000` `#262626`, set in `@layer base`) — both read as a washed-out near-black against a saturated accent card, not true black. Caught on `/family-survey`'s "Our two strongest scores…" cards: every text node was either explicitly `text-coal-900` or had no color class at all (silently inheriting `body`'s `#262626`) — fixed to explicit `text-coal-black` throughout. **Root cause, fixed at the source, not just this one instance:** `.card_base` (`global.css`) now sets `text-coal-black` as its own base color, so any future text node inside a card that forgets an explicit color class inherits true black instead of `body`'s wrong default — a safety net, not a behavior change, since every dark-filled `card_base` (`/book-adventure`'s wizard card, `/esa`'s results panels) already sets explicit accent colors on every element and is unaffected. Audited every other card sitewide (every page, plus every shared chart component — `card_stat`, `chart_donut`, `chart_bar_list`, `chart_segmented_bar`, `chart_vertical_bar`, `chart_table`, `chart_ranked_list`, `card_testimonial`) — all already used explicit `text-coal-black` or literal SVG `fill="#000"`; `/family-survey`'s hand-written cards were the only violation.
- **Rule 3 — no repeated accent in consecutive sections.** Two sections stacked back-to-back must not share the same dominant accent (card fill and/or heading color) — pick a different one of the 8 each time. Applies universally: per Rule 1, every section on the dark palette already has accent-colored text, so there's no "no accent treatment" case to exempt.
- **Rule 5 — one background for the whole page, no per-section tinting.** Every section (and the page `<header>`) on the dark palette uses `#1c1c1c` (`bg-dark-bg`) — full stop. Never an alpha-tinted accent wash (`bg-bina-purple/15`, `bg-bina-yellow/20`, etc.) and never a section-level `#000000`/`bg-coal-black` fill — `#000000` is reserved for cards (Rule 6), not whole sections. Section identity comes from its heading/text accent color (Rule 3), not from a background shift.
- **Rule 14 — one accent color per section, applied everywhere within it.** Every section has exactly ONE assigned accent color, set once (currently expressed via its heading/label color). EVERY element within that section — all cards regardless of how many, all data visualizations, progress bars/steppers, dividers, icons — must use that same single accent color. Nothing within a section introduces a second, different accent color of its own. The only exception is card *text*, which still follows Rule 2 (black text on an accent-colored card) — the card's own fill color, not just the text-on-it rule, must match the section accent. This is distinct from **Rule 3** (adjacent *sections* must use different accents from each other) — Rule 14 governs consistency *within* one section, Rule 3 governs variation *between* sections; they aren't in tension.
  - **A hero `<header>` and an immediately-following, heading-less continuation count as the same section for this rule** — e.g. `/student-results`' headline-stats grid (no heading of its own, sits directly under the grass h1) is part of the hero's section even though it's a separate `<section>` tag in markup; same for a stepper/progress indicator sitting right below a hero with no heading of its own.
  - **A multi-step wizard/flow is ALSO one section throughout, even though each step carries its own heading.** A genuinely new *topical* section (a page moving from "the school" to "the money" to "the reviews," say) earns its own accent per Rule 3's rotation — but a step's h2 inside one continuous interaction (`/book-adventure`'s "What is a bina Adventure class?" → "First, a bit about you" → "Now, about your child") is a state of the *same* flow, not a new topic, and stays on the flow's one accent throughout. Before this rule, each of those cases hand-picked its own one-off gray with no shared standard — `#a8a8a5`, `#6b6b68`, and (via a straight-up wrong token) `#313131` all showed up independently. **`#999999` on `#1c1c1c` is the only approved gray for this** — ~6:1 contrast, comfortably clearing the 4.5:1 AA minimum with margin, while staying visibly secondary to full-opacity primary text and accent colors. - **Rule 22 — every text element declares its own explicit color. Never rely on inheritance from a wrapper, and never rely on a browser or component default.** A `<p>`, `<span>`, `<li>`, `<dt>`/`<dd>`, `<td>`/`<th>`, `<summary>`, or any other text-bearing element gets its own `text-bina-*`/`text-coal-black`/`text-muted-gray`/`text-small` (or a dynamically-resolved equivalent, e.g. a `textClass`/`TEXT_CLASS[accentColor]` variable) — not just a size/typography-scale token, and not just a color set on some ancestor. This holds even when the color would *currently* render correctly via inheritance — the point is that it must not be able to silently stop working the next time an ancestor's class changes.
  - **Root cause, found on `/esa/[state].astro`'s closing CTA section:** the section wrapper (`<section class="bg-dark-bg text-bina-grass">`) set color once, intending every child to inherit it — and for plain elements (`<p>`, `<a>`) that actually worked, which is exactly what made the bug easy to miss. But `global.css`'s own base layer sets `h1, h2, h3, h4 { @apply ... text-coal-black; }` — a **direct** rule on every heading tag, and a direct declaration on an element always wins over an inherited value, regardless of specificity. The section's own `<h2>` had no color class of its own, so it silently fell through to that base-layer black instead of inheriting the wrapper's grass — rendering as near-invisible black-on-`#1c1c1c`, a Rule 1 violation. This is the concrete case of "a component or global style setting a default color that only shows through when nothing overrides it," and it is specific to heading tags — `p`/`span`/`li`/etc. have no such base-layer default, so they inherit correctly, which is precisely why this failure mode hides so well: most elements "just work" off inheritance, until the one that's a heading doesn't.
  - **How the color was lost, for the record:** git history shows this section originally read `bg-coal-black text-white` with the heading explicitly `text-white` (its own Rule 1 violation, just a different one). At some point both were corrected — the wrapper's background/color moved to `bg-dark-bg text-bina-grass` (right fix) — but the heading's own now-wrong `text-white` was simply deleted rather than replaced with `text-bina-grass`, on the unstated assumption that removing a bad color would let inheritance supply a good one. It doesn't, for a heading, for the reason above.

- **Rule 23 — icons follow the same never-white-on-dark rule as text: outlined style in the section accent on a dark background, outlined in `#000000` on an accent-colored card. Never a filled-white shape either place.** This covers standalone icons, an icon sitting in a circle badge, and an inline icon within a line of text — a checkmark, arrow, bullet/list marker, social icon, or status indicator is exactly as much "content on a background" as a text glyph, and Rule 1 (never black or white on dark) already governs it; this rule just spells out the specific *shape* the fix takes for an icon, where Rule 1 was written with text in mind.
  - **On a dark background** (`#1c1c1c` page or `#000000` card): the icon's own container (a circle, a pill) is outlined — transparent fill, a stroke in the section's accent color — and the icon glyph itself is drawn in that same accent (`stroke="currentColor"` on the glyph, with `color` set on the container, is the standard way to do this — see `ui_dropdown.astro`'s chevron or `ui_stepper.astro`'s checkmark for the reference pattern). Never a solid/filled circle, and never white for either the fill or the glyph.
  - **On an accent-colored card:** the icon's container is outlined in `#000000` (transparent fill, black stroke) and the glyph is black too — matching Rule 2's "text on an accent card is always black" logic applied to an icon instead of text. `card_prompt.astro`'s icon circle (transparent, `stroke="#000000"` border and glyph) is the reference implementation — it already matched this exact spec before this rule was written down, which is how existing prior art was found for it.
  - **Fixed this pass:** `/esa/[state]`'s hero gate-checklist ("bina is an approved Arizona ESA provider," "$7,000–$8,000 per child, per year," "You spend it through ClassWallet") — the checkmark badges were solid `bg-white` circles with a black tick (`border-coal-black`, `text-coal-black`), a Rule 1 violation reading as a near-invisible white blob against the dark hero and not matching this site's icon language anywhere else. Changed to `bg-transparent` with `border-bina-purple` and `text-bina-purple` (the hero's own accent) — outlined circle, accent tick, no fill. **Superseded by a later pass, noted so a future reader doesn't go looking for these checkmark badges and come up empty:** this whole checklist (icons included) was later removed outright and replaced with the hero fact-card row described in Rule 24 below — the icon-color fix above was correct for its time but the element it fixed no longer exists.
  - **Audited, not fixed, flagged as a separate finding:** `card_testimonial.astro`'s "See more" dialog has a `bg-white` "Close" **button** (with a text label, not an icon glyph — outside this rule's literal scope, but the same underlying Rule 1 problem: a solid white shape on the dialog's black background). Left alone since it's a labeled UI control rather than an icon and may be a deliberate, separate style choice — flagging rather than silently changing it.
  - **Everything else checked, already compliant, no change needed:** `ui_dropdown.astro`'s chevron, `ui_stepper.astro`'s checkmark, `pill_source.astro`'s external-link arrow, and `card_testimonial.astro`'s own external-link arrow all already use `stroke="currentColor"`, correctly inheriting an accent (dark-background instances) or black (accent-card instances, e.g. `card_testimonial`'s own text color) rather than a hardcoded fill. `card_prompt.astro`'s icon circle was already exactly right (see above). No other `bg-white`, literal white SVG `fill`/`stroke`, or filled circular icon badge exists anywhere else in the repo — checked every page and every component.
- **Rule 24 — when a section carries more than one kind of information, differentiate them visually rather than running them together in one string. Accent color for the section's primary message, muted gray for supporting/secondary facts.** A section can mix a genuine claim (the thing the section exists to say) with credentials or specs that back it up without being the claim itself — and if both are set in the same weight and color with no separation, a reader can't tell which is the point and which is supporting detail. This isn't a new color rule on top of Rules 1/2/14/16 — it's a rule about *when* to reach for the muted-gray tier those rules already define (Rule 16) instead of the section's accent, and about splitting one run-on string into separate, differently-weighted pieces instead of concatenating everything with a middot.
  - **Reference case: `/esa/[state]`'s hero.** The funding claim ("bina is an approved Arizona ESA provider," the award amount, the payment platform) is the section's actual message — stays the section's purple accent, one fact per card, each with a short bold value and a one-line supporting sentence (`card_stat` `fill="dark"`, default `labelColor="accent"` on the value, `labelColor="muted"` for the supporting line — see that component's own entry). The age range, school hours, and accreditations are credentials that back up the pitch but aren't the pitch — previously run into one middot-joined string ("Ages 4 to 15 · 5 hours a day, 5 days a week, about 200 school days a year · Cognia accredited · Registered online Cambridge International School · CIS member school") in the same purple as the claim above it, an unreadable run-on with no hierarchy between a legal-sounding accreditation name and the funding amount. Split into a row of individually outlined `pill_outline.astro` tags (see that component's entry), in muted gray — visually secondary, and no longer racing the funding claim for the reader's attention.
  - **The test for which tier a piece of text belongs to:** if the section stopped saying it, would the section's core claim still be true and complete? The funding amount and provider status are the claim itself — remove them and the section says nothing. The age range and accreditations are true regardless of whether this specific paragraph states them — they're supporting proof, not the message.
  - **This only ever applies to a black (`fill="dark"`/`bg-coal-black`) card or the page background directly, never an accent-filled card** — Rule 2 forces `#000000` text on an accent card with no room for a second, muted tier; the gray secondary tone is only possible because a black card's own fill is neutral (Rule 17's own note on this same mechanism, re: `/esa`'s results panel).

## 🔴 Layout & structure

- **Standard content container:** every section's outer wrapper is `mx-auto max-w-6xl px-8` — 1200px max-width, 32px side padding. `max-w-6xl` is overridden in `global.css` (`--container-6xl: 75rem`) to be exactly 1200px, since Tailwind's stock 6xl is 1152px — don't use the stock value or a different `max-w-*` size for a page's main section wrapper. (Narrower widths like `max-w-4xl`/`max-w-2xl` are still fine for intentionally narrow things — a centered CTA block, a readable paragraph line-length — those aren't "the container.") This was copy-pasted as `max-w-5xl px-5` on every page before being tokenized; if you see that pattern anywhere, it's stale and should be updated. **Alignment clarification (see Rule 13 below):** "intentionally narrow" never means giving a left-aligned content section its own narrower `mx-auto max-w-*` outer wrapper — that re-centers the whole section within the viewport and shifts its left edge inward relative to every other section's shared 1200px container, a real visible mismatch, not a stylistic choice. A genuinely narrow reading column (an FAQ list, a citation list, a paragraph) belongs *inside* the standard `max-w-6xl` outer wrapper as a plain (non-`mx-auto`) inner `max-w-*` div, which naturally hugs the same left edge as everything else — see `/family-survey`'s methodology section (`<div class="max-w-3xl"><ui_accordion .../></div>` nested inside its own `max-w-6xl` wrapper) for the reference pattern. The narrower `mx-auto max-w-4xl … text-center` wrapper stays reserved for an actually-centered block (Rule 13).
- **Rule 4 — no divider lines anywhere: not between stacked sections, and not between stacked content blocks inside a card either.** Sections on the dark palette are separated by spacing only (the existing `py-14`/`py-16` section padding is enough on its own) — never a `border-t`/`border-b` seam between them. **This extends inside cards too:** stacked paragraphs, a CTA row, a footnote — anything sitting inside one card/component — are separated by spacing/padding only, never a `border-t`/`border-b` line, even when the blocks above and below share the exact same background color. Caught on `/esa`'s JS-rendered results card: `border-t-2` seams stacked between same-colored pink blocks (a paragraph and the CTA row below it, the CTA row and the footnote below that) read as broken/redundant lines with no actual boundary to mark, since there was no color change at that seam to justify one — removed sitewide (`/esa` had 11 instances, `/esa/[state]` had 2: a header content-flow divider and a review card's quote-to-attribution divider). **One carve-out, about literal table structure, not page-flow content:** a data table's own header-row underline (`<tr class="border-b-2">`, e.g. `/family-survey` and `/student-results`'s score tables, and `chart_table.astro`) is structural to what it renders, not a decorative line cut into flowing content — that stays. A progress/step connector line (`ui_stepper.astro`'s `stepper-connector`) is a different element entirely — the connecting track between steps *is* the component, not a divider inserted into content — also out of scope. `/esa`'s three-fact grid used to lean on this same carve-out (a `grid gap-px bg-coal-black` block whose 1px gaps read as table-cell lines) — its later full redesign (see Rule 14) replaced it with a plain `grid gap-5`, no lines at all, so that instance no longer exists; the carve-out itself still stands for genuine tables.
- **Rule 11 — a section heading (or its intro paragraph, if one sits between the heading and the card) needs at least 32px of vertical space before any card that follows it.** This is the `--space-heading-card-gap` token in the Typography & Spacing section below (`mb-8`) — a deliberately narrower, purpose-specific minimum than the general `--space-heading-gap` (48px, `mb-12`), not a one-off number invented for this rule. "Card" means any `card_base`-based content — a single stat/data card, a `layout_sequence_steps` set, a card grid, a `<figure>` wrapping a chart. Measure from whichever element is *closer* to the card: if there's no separate intro paragraph, that's the heading itself; if there is one, it's the paragraph's own bottom margin that has to clear 32px, not the heading's.
  - **Caught on `/family-survey`**: five section headings sat directly above their card with only `mb-3` (12px) or `mb-6` (24px) — including the reported example, "And this is how it feels to be here…", where the card started almost immediately below the heading. All five fixed to `mb-8`. Every other instance on that page, and every instance on every other page (`/esa`, `/esa/[state]`, `/student-results`, `/reviews`, `/book-adventure`), already used a `mb-8` paragraph between the heading and the card — that pattern turns out to already be the sitewide norm; the five fixes were the exceptions, not the rule.
  - **`/esa` had one direct violation** (`mb-3` heading straight into a card, no paragraph between) — fixed the same way, to `mb-8`.
  - This rule doesn't touch heading→FAQ or heading→CTA-button spacing (still governed by `--space-heading-gap`/48px or handled case by case) — it's specifically about the transition into a card.
- **Rule 13 — section alignment: left by default, centered only for closing/decision moments.**
  - **Left-aligned is the default for every section** — headings, body text, data/stat content, cards. This supports scanning dense or evidence-heavy content the way an article or report does, and keeps ragged-edge readability issues out of longer text.
  - **Centered alignment is reserved specifically for a page's single closing CTA section** (and optionally its hero) — never for a mid-page content section like a data display, a tab/level selector, or an explanatory intro. Centering signals a deliberate shift from "read this" to "now decide"; using it anywhere else weakens that signal and makes the page feel inconsistent rather than intentional.
  - **A section's container alignment must always match its text alignment.** Left-aligned text needs a left-anchored container — not a narrower `mx-auto max-w-*` box centered within the viewport while the text inside reads left, which shifts that section's left edge inward relative to every other section's shared 1200px container (a real, visible mismatch — see the Standard content container note above for the correct nesting pattern). Centered text needs a fully centered container (`mx-auto` + `text-center` together, as the closing-CTA sections already do).
  - **Caught sitewide:** `/esa`'s "See your state's exact steps", `/student-results`' "See results for your child's age group", and `/esa/[state]`'s "Your Tuesday, if your child were at bina", its FAQ section, and its "Where these numbers come from" section were all sitting in a narrower `mx-auto max-w-4xl` (or `max-w-2xl`) wrapper with plain left-aligned text — every one widened to the standard `mx-auto max-w-6xl px-8 py-[clamp(3rem,6vw,6rem)]` outer container (the FAQ section's own reading-width narrowing moved to a plain inner `max-w-3xl` div, matching `/family-survey`'s already-correct pattern). Every closing CTA section sitewide (`/reviews`, `/student-results`, `/family-survey`, `/esa/[state]`) already paired `text-center` with its narrower `mx-auto` wrapper correctly and needed no change.
  - **`/book-adventure` is a deliberate exception, not a violation:** its entire page — hero and wizard card alike — uses a narrower container throughout (it's a single-column campaign funnel, not a page built from `max-w-6xl` content sections), so there's no wider sibling section for it to visibly mismatch against. Don't widen it to `max-w-6xl` to "comply" — that would fight the page's own one-column design instead of fixing an actual inconsistency.
- **Rule 17 — content containers are at most two levels deep: the page background, and at most one card/panel on it. Never nest a card inside a card.** A "content container" here means anything acting as its own visual surface — a card, a panel, a results/summary block, a section wrapper with its own background fill. The page background (`#1c1c1c`) is level one; at most one card/panel (`#000000` or an accent fill) is level two. A third level — a card nested inside that card — is never allowed, no matter how tempting it is to group a subset of the card's own content (a "facts" cluster, a status block) behind its own second fill color. Group with spacing, headings, and label/value hierarchy instead (Rule 4's spacing-not-dividers principle, extended one level deeper).
  - **Explicit exemption — inline elements are not a surface level and may sit directly on a card without violating this rule:** status pills, tags/badges, number circles (a `layout_sequence_steps`-style step number, a `ui_stepper` circle), icon circles, and buttons (`.ui_button`/`.ui_button_ghost`). These are small, inline-scale UI chrome, not content-grouping surfaces — a pill sitting on a card is not "a card inside a card" the way a second full-width panel is. Written down explicitly here so a future nesting-depth audit doesn't strip these out by treating every filled shape as a violation.
  - **Fixed this pass — `/esa`'s state-tool section, four levels down to two.** Before: `#1c1c1c` → an outer purple `card_base` (holding the intro paragraph, the "which state" label, and the `ui_dropdown`) → a black `card_base` (the JS-rendered results panel) → a purple `card_base` nested inside *that* (the "facts" cluster — who/how-much/how-it-works). Four surfaces for what's really one decision (pick a state) and one result (here's your path). After: the outer purple card is gone — heading, intro paragraph, label, and `ui_dropdown` sit directly on `#1c1c1c` in the section's own purple accent; the black results panel is now the page's only card, holding everything — state name, program name, status pill, the three fact columns, and the full numbered step list — with the facts rendered as plain label/value pairs directly on the black, no wrapping card of their own. Two levels: page background, one card.
  - **This is also what unlocks gray secondary text inside the results panel** (fact column labels, step descriptions) — worth spelling out since it's easy to miss and easy to "fix" back incorrectly later. Rule 2 forces `#000000` text on an *accent-filled* card (there's no room for a muted gray tier there — black is already the only legible choice). A **black-filled** card has no such constraint: its own fill is neutral, so `--color-muted-gray` (`#999999`, Rule 16) reads clearly on it and correctly recedes behind the card's primary text (`#b38cff`) the way de-emphasized text is supposed to. Flattening the nested purple facts card into the outer black one didn't just remove a surface — it's the specific move that made real gray secondary text possible here at all. Don't reintroduce a nested accent card "to group the facts visually" without remembering it would also force those labels back to black, undoing this.
  - **The ui_dropdown's own fill changed too, as a direct consequence, not a separate decision.** It used to sit on the purple card and (per `ui_dropdown.astro`'s own established design) kept a solid dark fill regardless of what color card it was dropped onto. With the purple card gone, the ui_dropdown now sits directly on `#1c1c1c` — its "immediate background" is the plain page, the exact case Rule 9 already governs (outline only, no fill, accent border/text). `ui_dropdown.astro` gained a `fill?: 'dark' | 'none'` prop for this — `'dark'` stays the default (preserves the component's original behavior for any future reuse on a colored card), `/esa` now passes `fill="none"`.
  - **Fixed this pass — `/student-results`' "See results for your child's age group," three levels down to two.** Before: `#1c1c1c` → an orange `card_base` (holding the age-group tab buttons and a `#level-result` mount point) → 1-3 black `rounded-2xl bg-coal-black` tiles rendered into that mount point by a client-side `bigStat()` JS function, one per stat. After: the orange card is gone from around the *tabs* — the tabs now sit directly on `#1c1c1c`, styled per Rule 9's dark-background case (unselected: `accentColor` outline + text, no fill; selected: filled `accentColor`, `#000000` text — a change from this component's *previous* default of a black-fill selected state, deliberately, for this instance). One orange card remains, below the tabs (32px gap, Rule 11), holding the stat number, label, sub-detail line, and both explanatory paragraphs — all `#000000` (Rule 2) — with no card of any color nested inside it.
    - **Componentized in the same pass, not left as page-specific markup**, per the request that flagged this: the tab row + single-result-card shell is now `section_tabbed_stat.astro` (`src/components/sections/`) — see its own catalog entry below. `card_stat.astro` was reused for the 3 stat tiles rather than duplicated, extended with a new `fill="none"` variant (no card of its own, `#000000` text) specifically so several `card_stat`s can sit inside one shared parent card without each one becoming its own nested surface — see `card_stat`'s own catalog entry for the full before/after. `layout_stat_section.astro` needed no change at all — it was already just the outer `eyebrow`/`h2`/intro shell sitting on `#1c1c1c`, unrelated to the nesting violation, which was entirely inside its default slot.
    - **A real script-ordering bug surfaced verifying this, worth recording so it isn't reintroduced:** `section_tabbed_stat`'s click-handling script initially used Astro's default deferred-module script (like most components in this repo). `/student-results`' own page script uses `define:vars` to read `?level=` deep-link state — and `define:vars` implicitly makes a script `is:inline`, meaning it runs *synchronously at its position in the document*, not deferred. On a fresh page load with `?level=M1` in the URL, the page's inline script tried to `.click()` the matching tab *before* the component's deferred module script had run and attached its click listener — the click did nothing, and the page silently fell back to the default tab. Confirmed both broken and fixed via direct browser testing, not just reasoning about it. Fixed by making `section_tabbed_stat`'s own script `is:inline` too (plain JS, no TypeScript syntax, since `is:inline` scripts are injected as-is and never passed through Astro's bundler) — the exact same reason `ui_dropdown.astro`'s setup script already uses `is:inline`. **Any component meant to be driven by a page's own `define:vars` script needs to attach its listeners via `is:inline`, not a deferred module** — this is the second component to need this fix, so it's a pattern to check for by default in a new interactive component, not a one-off surprise each time.
  - **Interaction with Rule 14 (one accent per section) for multi-color data-viz cards:** a chart that legitimately needs more than one color to stay legible (Rule 14's own carve-out — e.g. `/student-results`' distribution-curve legend, autumn vs. spring, chosen for CVD-safe separation) still lives on exactly one card, and that card is still level two, sitting directly on the page background like any other. Rule 17 doesn't add a new constraint here beyond what's already true — multi-color content inside a card is fine (it's data, not a second nested surface); a card of any kind (including a black one used specifically to host multi-color data-viz) is still never placed *inside* an accent card. If a future multi-color chart card is ever built as a black card nested inside a section's accent-colored outer card "to separate the chart from the rest," that's exactly the Rule 17 violation this rule exists to catch — the chart's own card and the section's accent card must be siblings on `#1c1c1c`, never parent/child.
  - **One confirmed, narrow exemption: a native `<dialog>` opened via `showModal()`.** `card_testimonial.astro`'s "See more" dialog (`<dialog class="testimonial-dialog card_base">`, `background: #000`) is, in the raw DOM, a black `card_base` nested inside the testimonial's own accent-tinted `card_base` — the literal shape Rule 17 bans. It's exempted because a native `<dialog>` opened with `.showModal()` renders in the browser's *top layer*, a rendering layer entirely outside normal document stacking — it's never visually painted "inside" its parent card's box (the dialog centers over its own backdrop, and the parent card is not simultaneously visible behind it the way a real nested panel would be). Rule 17 is about visual surfaces stacking on top of each other; a top-layer modal doesn't do that regardless of its DOM position. Don't extend this exemption to anything that isn't an actual native `<dialog>`/`showModal()` pair — a hand-rolled "modal" built from a plain positioned `<div>` doesn't get this pass, since it *would* actually nest visually.
  - **Sitewide audit, this pass — two violations found and fixed (`/esa`, `/student-results`, both above), everything else already compliant.** Checked every page (`/reviews`, `/family-survey`, `/book-adventure`, `/esa/[state]`, `/student-results`) and every shared component that renders a card (`card_stat`, `section_tabbed_stat`, `layout_sequence_steps`, `card_text`, `card_prompt`, `pill_label`, `ui_dropdown`, `layout_footer_simple`, `layout_footer_complete`) for the same nested-card pattern. Every other card sitewide already sits directly on `#1c1c1c` (via a plain `bg-dark-bg` section or `layout_stat_section`, which itself has no fill of its own) with nothing but inline-exempt chrome (pills, buttons, icon circles) or genuine siblings (a grid of same-level cards, never one inside another) inside it. `/esa/[state]` is the densest page on the site for cards and was checked card-by-card — every one confirmed a direct child of its section, none nested inside another.
- **Rule 19 — text inside a card wraps at the card's own content width, never a narrower fixed width, unless there's a deliberate measure constraint.** A card's text (labels, notes, paragraphs, anything) should break lines only where the card's own padding/edges force it to — the same width every other text block in that card uses. Never let a *layout* element sitting *around* the text (a grid track, a flex basis, a fixed-width column) squeeze it narrower than the card's content box for no content reason. **Never use a hardcoded `<br>` to force or prevent a line break** — a line break is a layout outcome, not something to author by hand; if text is breaking somewhere ugly, fix the container that's constraining it, don't paper over it with a manual break (which will just land wrong again the moment the copy or viewport changes).
  - **"Deliberate measure constraint" is a real, narrower exception** — a genuinely intentional reading-width cap on a long paragraph (e.g. `introClass="max-w-2xl"` on a `layout_stat_section` intro, or a centered CTA block's `max-w-xl`) is fine; that's a typographic choice about line length for readability, made on purpose, and documented as a prop/class at the point of use. What this rule bans is an *incidental* width squeeze — text losing width because it happens to sit inside one cell of an N-column grid alongside other content, with no reading-width intent behind the number of columns.
  - **Caught on `/student-results`' per-level result tool ("See results for your child's age group")**: the three `card_stat`s (or, for P1/P2, the one `card_stat` — `readGrowthMedian` is `null` for those two levels, so only the first stat renders) sat in a `grid gap-3 sm:grid-cols-3` wrapper, which reserved three equal ~1/3-width columns regardless of how many cards were actually present. Every card's label and note wrapped inside that ~349px column — visibly narrower than the plain paragraphs directly below the grid, which ran the panel's full ~1072px width — producing exactly the "orphaned word" look this rule exists to prevent (e.g. "spring '26" or "reading" alone on its own line). No `<br>` was involved; the constraint was the grid's own column track. Fixed by dropping `sm:grid-cols-3` — the wrapper is now a plain single-column `grid gap-4`, so every stat card (whether 1 or 3 are present for a given level) is full panel width, matching the paragraphs below exactly. Verified across all seven tabs (P1–M1): every label and note now renders on one line, and the fix holds even for M1's longer interpolated strings, which don't just happen to fit — they were the tightest case checked.
  - **This is a general authoring rule, not scoped to `card_stat` or `/student-results`** — the next time a card's text looks like it's breaking earlier than it should, check for the same shape of bug: a grid/flex ancestor sizing a column by track count rather than by content, not a font-size or `max-width` on the text element itself (which is usually where the eye goes first, and usually not where the real constraint is).

## 🔴 Typography

### Typography & spacing — extracted from thebinaschool.com

thebinaschool.com (`Bina-School-R-D/website`, cloned locally at `~/Documents/website` for reference — re-clone if it's gone) has **no central type-token file**: every component sets `fontSize` inline, mostly `clamp()`, chosen per-section rather than off one shared scale. So "match the site" means matching its most-repeated values, not quoting a token file. The values below are our distillation — each one recurs 3+ times across the site's own components — turned into real `@theme` tokens in `global.css` so this repo has the single scale the source never bothered to name.

**Typography scale** (`--text-hero`, `--text-section`, `--text-button` in `global.css`, each paired with its own `--text-*--line-height`; always combine with `font-display`, never a one-off `text-[…]` or stock `text-4xl`/`text-3xl` size). **Renamed from `--text-h1`/`--text-h2`** once those names were needed for bina's official type scale (see the "Typography" section below) — same values, same behavior, just renamed; don't confuse these with the unrelated `text-h1`/`text-h2`/`text-h3` classes that scale now owns.

Rules:
- **A section heading is always `text-section font-display`, never a one-off `text-3xl`/`text-2xl` size.** The one exception is a compact sub-heading genuinely nested *inside* a narrower container than a full page section (e.g. a step label inside a campaign wizard card, or a quiet "where these numbers come from" methodology subhead) — those stay smaller by design; don't force them up to `text-section` just because the element is an `<h2>`.
- **The page's single hero heading is always `text-hero font-display`.** Don't repeat `font-black` on it — `@layer base` already sets `font-bold` (700) on every `h1`–`h4`, which matches the site's actual h1 weight; an explicit `font-black` (900) was a drift from that, not an intentional choice, and has been removed everywhere it appeared.
- **`layout_sequence_steps.astro` is a deliberate, documented exception** — its number/title/description sizes are fixed pixel values (60px/32px/18px), not a fluid token. That was an explicit correction (see the component's own catalog entry below): a long single word in a `clamp()`-sized title overflowed a narrow grid column. Don't "fix" it back to a fluid size — and see Rule 10's component-spec audit above for how these three fixed values map onto bina's official scale (title → `Subtitle2`, description → `Body3`; the 60px number is a documented tie between that scale's `H1`/`H2`, flagged there for a call).
- **`ui_accordion.astro`** was built by extracting the source's own FAQ styling directly and is already aligned; it doesn't need the scale applied on top.

Rules:
- **Every section wrapper uses `py-[clamp(3rem,6vw,6rem)]`**, not a flat `py-14`/`py-16 sm:py-20`/etc. — that heterogeneous set (found across every page) has been swept to this one value.
- **A heading directly stacked on top of its own single stat/number keeps its existing tighter margin** (`mb-3`/`mb-4`) rather than `mb-12` — that's a deliberate close-pairing between a claim and its number, a different relationship than "heading, then a paragraph or grid," and the source has no equivalent pattern to extract a rule from. Don't blanket-apply `mb-12` to every heading; use it for heading→paragraph and heading→non-card-list gaps specifically. **When a card follows instead, Rule 11's 32px (`mb-8`) floor applies, not this 48px token** — see below.
- Internal component gaps below the card-grid level (badge padding, icon gaps, stat-row spacing) are page-specific and tuned per content — they're intentionally out of scope for this token set.

### bina's official type scale

**Rund Display is the only font on this site — full stop.** Rund Text (a second, separate typeface this repo used to load for body copy) has been removed entirely: its `@font-face` block and its five `.woff2` files are gone from the repo, and `body`'s own base style now defaults to `font-display` instead of the old `font-sans`. There is no other font anywhere — no Google Fonts, no system-font fallback stack beyond the `Arial, sans-serif` safety net baked into `@font-face` itself, no per-component exception. Body copy, captions, headings, buttons, chart labels — everything is Rund Display; **only the weight changes per step**, never the family.

**No font size outside this scale may be used anywhere on a GTM page.** That includes literal Tailwind classes that happen to produce an off-scale pixel value (`text-2xl`/24px is fine since it equals Body1, but `text-3xl`/30px or `text-4xl`/36px are not on the scale and shouldn't be reached for) and arbitrary bracket values (`text-[32px]` is fine since 32px is Subtitle2, but `text-[35px]` or similar off-scale values are not). If a design genuinely needs a size this scale doesn't have, that's a scale gap to raise, not a value to invent locally.

**The scale** (Figma "bina website AUTO LAYOUT" library). Every step: 100% line-height, 0 letter-spacing, Rund Display.

| Token | Size (mobile → desktop) | Weight | Tailwind class |
|---|---|---|---|
| Display1 | 80px → 96px | **Black (900)** — see note below | `text-display-1` |
| Display2 | 64px → 80px | **Black (900)** — see note below | `text-display-2` |
| H1 | 56px → 64px | Bold (700) | `text-h1` |
| H2 | 48px → 56px | Bold (700) | `text-h2` |
| H3 | 40px → 48px | Bold (700) | `text-h3` |
| Subtitle 1 | 32px → 40px | Bold (700) | `text-subtitle-1` |
| Subtitle 2 | 24px → 32px | Bold (700) | `text-subtitle-2` |
| Body1 | 20px → 24px | Medium (500) | `text-body-1` |
| Body2 | 18px → 20px | Medium (500) | `text-body-2` |
| Body3 | 16px → 18px | Regular (400) | `text-body-3` |
| Small | 16px (flat) | Regular (400) | `text-small` |

Each class is a single Tailwind v4 `@theme` token carrying size, weight, line-height, and letter-spacing together (`--text-<name>`, `--text-<name>--font-weight`, `--text-<name>--line-height`, `--text-<name>--letter-spacing`) — apply the one class, no separate `font-bold`/`font-medium` needed alongside it. Responsive scaling is a real two-point `clamp()` (375px mobile viewport → 1280px desktop viewport, "one step down" mobile values — see `global.css`'s own comment on the token block for the full formula and reasoning), not a hard breakpoint jump.

**`Display1`/`Display2` are reserved specifically for emphasized numbers — a headline stat figure ("70%", "9.42", a big count-up) — never for a hero/section heading, however large the moment feels.** `H1` (64px) stays the largest permitted *heading* size on any GTM page; that hasn't changed. This is a narrower, purpose-built pair, not a "bigger H1."

**Correction to an earlier version of this section:** these two steps were previously assumed to be the source library's own `H1`/`H2` (96px/80px, reserved and unused), with GTM's own `H1`/`H2`/`H3` framed as "the library's H3/H4/H5, renumbered." That was wrong — checked directly against the Figma panel, and 96px/80px are their own named category, `Display1`/`Display2`, entirely separate from the library's H-scale. **There was never a naming collision or a renumbering** — GTM's `H1`/`H2`/`H3` map straight onto the library's own H3/H4/H5 (GTM pages just never needed anything as large as the library's actual H1/H2), and `Display1`/`Display2` now fill that "very large" register for the one thing that genuinely needed it: big emphasized numbers, e.g. `chart_donut`'s `variant="number"` display (previously a bespoke `text-7xl sm:text-8xl`, now `text-display-1`).

**Both `Display` steps are Black (900), not the source library's specified ExtraBold (800) — a deliberate, confirmed substitution.** No ExtraBold weight file exists for Rund Display, not in this repo and not in thebinaschool.com's own (checked directly — its own `@font-face` comment states "Regular/Medium/SemiBold/Bold/Black only per design system," matching the five weight files actually shipped here). Requesting `font-weight: 800` with only 700 and 900 available would leave the browser's own font-matching algorithm to decide — implementation-defined, not something to leave to chance for the site's biggest visual numbers. Black was confirmed explicitly as the substitute. If the real ExtraBold file is ever sourced, swap the weight token in `global.css`, not the pixel values.

**Naming collision with this repo's own older tokens, resolved by renaming, not deleting:** this repo already had `--text-h1`/`--text-h2` tokens before this scale existed — a *different*, fluid-clamp system extracted from thebinaschool.com for the page hero and section headings (56px→84px and 32px→56px respectively). Those were renamed to `--text-hero` / `--text-section` specifically to free `h1`/`h2` for the official scale above; all 16 live usages across every page were migrated to the new names. The two systems now coexist under different names — `text-hero`/`text-section` for the site's own extracted fluid headings (still valid, still in use, not being retired), `text-h1`/`text-h2`/`text-h3` for bina's official fixed scale. Don't confuse the two just because the old name is now free.

**Which step for what:**
- **An emphasized number/stat figure** — `Display1` or `Display2` (96px/80px), e.g. `chart_donut`'s big `variant="number"` display. Never a heading, however prominent the moment — this pair is for digits, not words.
- **Hero/page heading** — `H1` (64px). The single largest *heading* permitted on a GTM page. *(Most existing page heroes currently use the older `text-hero` fluid token instead, not `H1` — the two aren't equivalent and haven't been reconciled; see the note below.)*
- **Section heading** (the heading introducing a `layout_stat_section` or similar page section) — `H2` or `H3` (56px/48px) depending on how much visual weight the section needs relative to others on the page. *(Same caveat: most currently use `text-section`.)*
- **Card title / sub-heading inside a section** — `Subtitle 1` or `Subtitle 2` (40px/32px) — e.g. a `card_text` title, a card's own internal heading.
- **Primary reading/body copy** — `Body1` or `Body2` (24px/20px) — intro paragraphs, explanatory text inside a stat card, general body copy. `Body2` is the more common default (matches the old 20px primary tier in Rule 10 below); reach for `Body1` when a passage specifically needs to read as more prominent than typical body copy.
- **Compact/secondary text** — `Body3` (18px) — footnotes, chart legends/axis labels, table cells, tags/pills, link and button text. Matches Rule 10's existing 18px secondary tier exactly.
- **Captions and true fine print** — `Small` (16px) — the absolute floor; genuine legal/copyright text only, per Rule 10.

**Step 5 (applying this scale to every page's actual markup) is done for `Body1`–`Small` and every component that used a raw Tailwind size class or an arbitrary bracket value** — see the shared-component and page-by-page notes throughout this file's component catalog for exactly what changed where. Two things remain open, tracked here rather than silently assumed finished:
- **`text-hero`/`text-section` were deliberately kept, not migrated to `H1`/`H2`.** They're a different, older fluid-clamp system (56px→84px / 32px→56px) still governing every page's actual hero and section headings; reconciling them with the new `H1`/`H2`/`H3` (or deciding they should stay permanently separate) is an open decision, not an oversight.
- **`Display1`/`Display2` have only been applied to `chart_donut`'s number variant so far** — a sitewide check for any *other* emphasized-number display that should adopt them (beyond the one gap this pair was added to close) hasn't been done yet.

- **Rule 10 — a three-tier scale for content text: 20px primary, 18px secondary/supporting, 16px true fine print only.**
  - **Maps directly onto bina's official type scale (see the "Typography" section above) — use the token names, not raw pixel values, in new code.** Primary = `text-body-2` (Body2, 20px), secondary/supporting = `text-body-3` (Body3, 18px), fine-print floor = `text-small` (Small, 16px). Existing Tailwind classes (`text-xl`/`text-lg`/`text-base`) still resolve to the same three pixel values today, so nothing visually changes — but a full sitewide migration to the token classes is tracked separately (see "Typography" section, Step 5) rather than done piecemeal here.
  - **Primary reading/body text is 20px (`text-xl` / `text-body-2`)** — the standard size for any substantive paragraph a reader is meant to read start to finish: intro paragraphs sitting under a heading, explanatory text inside a stat/data card, general body copy. This is the size to reach for by default; drop to the tiers below only for the specific categories they name, not just "it feels a bit long for a caption."
  - **Secondary/supporting text is 18px (`text-lg` / `text-body-3`)** — a wide category, not just "compact cards": footnotes and methodology notes (e.g. "Middle-school parent survey, 108 responses…"), chart/graph legends and axis labels (e.g. "STAR scaled scores, 108 students," the "Oct '25"/"May '26" date markers on a chart), tags/pills (e.g. "with bina," "on your state's site"), tab sub-labels (e.g. "ages 6–7" under a "P2" tab), link and button text, table headers and cell content, toggle affordances (e.g. "See the numbers"), and step sub-headings inside a compact numbered-list component (e.g. `/esa`'s "Talk to bina first"). `card_testimonial.astro` set this precedent first (a `/reviews`-specific pass, before any of this was a sitewide rule): description text at 18px. Testimonial/review cards stay as their own confirmed exception either way.
  - **16px (`text-base` / `text-small`) is true minimum/fine print only** — reserve it for the smallest legal/disclaimer text on the page, e.g. a footer copyright line. **This is a correction to an earlier version of this rule**, which put footnotes, methodology notes, table cells, chart axis labels, badge pills, and source/attribution lines at this floor tier — those all belong at 18px (the secondary/supporting tier above), not 16px. 16px is now reserved specifically for genuine legal/copyright fine print, not general "small text."
  - `text-hero`/`text-section` (the site's own extracted fluid hero/section headings — renamed from `text-h1`/`text-h2` once those names were needed for bina's official scale) and `text-button` are untouched, already well above any of these tiers. The old `text-h3` and `text-small` fluid tokens (28px→40px and 14px→30px respectively) were dead code — nothing referenced either — and were deleted outright rather than renamed; `text-small` now names a step in the new official scale instead (16px flat, see "Typography" below), a different value with the same name, so don't go looking for the old 14px→30px behavior under that name anymore.
  - **A decorative, `aria-hidden` icon glyph is not "text" for this rule** — e.g. a tiny fallback initial-letter mark standing in for a missing logo image inside a small circular badge. It's still worth sizing sensibly for whatever space it sits in, but it's exempt because a screen reader never encounters it as content. Everything else — anything a sighted reader is meant to actually read — is in scope, no matter how small its role on the page.
  - **Two sweeps got the tiering wrong before this one landed — both corrected here, worth naming so a third pass doesn't repeat either mistake.** First pass (18px→20px default): fixed the 20px tier broadly, but reused 18px only for `card_testimonial`-style compact cards, not yet as its own defined "supporting text" category — so hero/closing-CTA paragraphs across every page and several unstyled card paragraphs (`/family-survey`'s "Where these numbers came from" trailing paragraph, `/esa/[state]`'s four un-migrated sections, `/book-adventure`'s wizard step-1 text, `card_stat.astro`'s `label`/`note`) were bumped to 20px, which was correct for those (genuine reading paragraphs). Second pass wrongly pushed footnotes, chart legends/axis labels, and table cells to the 16px floor or, in `chart_table.astro`'s case, all the way to 20px — neither was right; **this pass moves that entire category to 18px**, its actual home. Swept for the 18px secondary-text tier: `/family-survey`'s "12-month plan" and "whatever comes after bina" footnotes, `/student-results`' tenure-chart footnote, the distribution-curve cards' legend/axis labels/"See the numbers" toggle/table/footnote, the per-level tool's `P1`–`M1` tab labels and their "ages X–Y" sub-text and result-card supporting lines, and `/esa`'s entire results panel (step sub-headings, tags, inline links, funding-renewal note, CTA button label text, and the closing disclaimer). `chart_segmented_bar.astro`'s legend, bumped to 20px in an earlier pass under the "everything in this card is content" reasoning, moved down to 18px too — it's a legend, which this rule now explicitly places at the secondary tier; leaving it at 20 while every other legend sitewide sits at 18 would just be a fresh inconsistency of the same kind this rule exists to prevent. `chart_table.astro`'s cells came down from 20px to 18px, matching "table headers/cells" being named at this tier explicitly. **The sitewide sweep this correction also required (beyond the named list) turned up the same 16px-floor mistake in several more places**, all now 18px: `pill_label.astro`'s pill text (every page's hero/section category tag), `layout_stat_section.astro`'s eyebrow label (used by every stat section on `/family-survey`, `/student-results`, `/esa/[state]`), `pill_source.astro`'s name/rating text, `chart_ranked_list.astro`'s row note, `/reviews`' "As seen on" label, `/student-results`' "independent"/"adaptive"/"nationally normed" pill tags and its growth-footnote, `/book-adventure`'s two consent/helper lines, and — spread across `/esa/[state]` — the hero's age/day/accreditation line, the funding card's `dt`/`dd` fact pairs and its rules-disclaimer paragraph, the tier-status pill, the feature-card eyebrows, the day-in-life time labels, the timing-card body, the review-card attribution line, the closing "Prefer email?" line, and the entire "Where these numbers come from" methodology list — the last of these a second, page-specific instance of the exact "methodology notes" category the correction opened with. **Chart-component SVG text was a separate, related miss**: `chart_donut.astro`'s ring unit label, `chart_vertical_bar.astro`'s two axis-label classes, and `chart_bar_list.astro`'s three axis/suffix-label classes were all sub-18px literal `font-size` values in each component's own `<style>` block (17px or 16px) — the same "axis label" category as `/student-results`' `.chart-label`, just easy to miss because they're CSS, not a Tailwind class. All raised to 18px.
  - **One instance stays below even this, as a confirmed, narrower exception:** `/esa`'s JS-rendered results-panel step *description* text (the muted-gray `#a8a8a5` prose under each numbered step, as opposed to the step's own bold heading) is also 18px — already correct from an earlier pass, unaffected by this one.
  - **Component-spec sizes checked against the official scale — most already land on a real step; two flagged sizes turned out to be misreported and were corrected here rather than mapped as given:**
    - `card_testimonial.astro`: name/source line/source-link/button text (all 16px) → `Small`. Description (18px) → `Body3`. Every value already an exact scale step, nothing rounded.
    - `layout_sequence_steps.astro`: title (32px) → `Subtitle2` (exact). Description (18px) → `Body3` (exact). The number (60px, fixed, not a fluid token) does **not** land on a step — it sits exactly between `H2` (56px) and `H1` (64px), a genuine tie, not a close call either way. Rounding up to `H1` is the alternative if the visual weight is judged too light — flagging for a call, not deciding unilaterally given it's an exact tie.
    - **`card_stat.astro` has no 32px size anywhere** — its value is 48px (`text-5xl`, → `H3` exactly) or 30px (`text-3xl`, the `valueSize="md"` variant — does **not** land on a step; nearest is `Subtitle2` at 32px, 2px off, recommend rounding to that), and its label/note are both 20px (`text-xl`) → `Body2` exactly.     - **Chart label rules** (Rule 20/21's "18px category labels," `chart_donut`/`chart_bar_list`/`chart_vertical_bar`/the bell-curve's `.chart-label`) → `Body3` exactly, all of them — this was already the established convention (Rule 10's own history above), the token name is just new.
    - None of this has been applied to any component's actual markup yet — this is the mapping table for Step 5 (page-by-page token migration) to follow, not a statement that the migration is done.
  - **A third pass regressed the exact `chart_vertical_bar`/`chart_bar_list` fix named above, worth recording since it's now happened twice.** While adding a size *hierarchy* between a chart's bold value labels and its regular category/axis labels, `.vbc-label-sm` and `.pbl-label-sm` were both dropped below `18px` (`11px` and `12px` respectively) — deliberately, to counteract each SVG's own `viewBox` scale and land closer to a *literal* 18px on screen at the component's standard card width. That's still a real Rule 10 floor violation: the rule is about the declared value in the stylesheet, with no carve-out for "but it renders bigger than declared because it's inside a scaled SVG." Reverted both to literal `18px`. **The underlying hierarchy request (values should read as more prominent than category labels) is legitimate, but font-size is not an available lever for it inside these SVGs without breaking the floor** — weight and typeface (bold `Rund Display` vs. regular `Rund Text`) are what already differentiate them, and that's the only lever to use. If a real size gap is ever wanted, the value label would need to go *up* (e.g. to a larger literal size, still ≥16px) rather than the category label going down.

## 🔴 Cards & surfaces

- **Rule 6 — data/stat cards: full content grouping and color matching.** Any section built around a number, stat, or chart (donut, score, percentage, etc.) follows this structure:
  - The section heading sits directly on `#1c1c1c` — never inside a card.
  - Everything else — the stat/chart itself AND its supporting/explanatory text — goes together inside ONE card. Do not isolate the number alone on a card while its explanatory text sits outside on the page background.
  - **The card's background color matches the section's accent color (the same color used in the heading) — EXCEPT where the card's content is multi-color data visualization, in which case Rule 18 applies instead and the card is black.** Outside that exception, it is NOT always black either way — a black card can still occur when the section's assigned accent color for that position in the rotation happens to call for a black/dark card treatment specifically (e.g. `/esa`'s results panel, black with a single lila accent throughout) — but that's a different, non-Rule-18 reason, unrelated to the content being multi-color. **"Multi-color" here means "carries any accent-colored graphic mark of its own" — Rule 18's own corrected reading (see that rule) — not literally "two or more colors."** A single-fill donut ring, progress bar, or vertical-bar-chart column is exactly as much a Rule 18 case as a genuinely multi-color chart; don't read this bullet as exempting single-fill charts.
  - Text and numbers inside the card are `#000000` **only when the card itself is accent-filled** (per Rule 2). On a Rule 18 black card, Rule 2 doesn't apply — text there follows Rule 1 instead (the section's own accent color, never black or white).
- **Rule 12 — card containers never get a stroke/border.** Applies to the outer container of any card — stat cards, testimonial cards, CTA cards, sequence-step cards, review cards, results/summary panels, anything built on `.card_base` or an equivalent hand-rolled rounded container. The card is just its solid background color and rounded corners — no `border`/`border-2`, no outline of any kind around the card itself. This is scoped to the outer container only and does **not** change two other, unrelated uses of strokes on this site: the black stroke on progress-bar/donut fills (Rule 7) and the outlined style on tabs/selectors/dropdowns (Rule 9) — both exist for contrast/definition on small interactive or data-viz elements, a different job from a card's own boundary, and stay exactly as they are.
  - **`.card_base` itself** (`global.css`) carried `border-2 border-coal-black` since the very first version of this site — removed. Since almost every card sitewide is built on this one shared class, that single edit fixed the vast majority of instances automatically.
  - **Hand-rolled cards not using `.card_base` needed their own fix:** `/esa`'s two JS-rendered results-card containers (`rounded-[1.875rem] border-2 border-coal-black` → border removed, radius kept), `/student-results`' JS-rendered `bigStat` card (`border-2 border-dark-border` removed).
  - **`card_prompt.astro`'s root briefly carried a NAMED exception to this rule** — a 2px `accentColor` border, reinstated for one pass after `card_testimonial.astro` moved to one uniform accent per grid, so `card_prompt` would still read as distinct from its now-uniform neighbors. That border is gone again: `card_prompt` now differentiates itself with a solid accent *fill* instead (see its own catalog entry below), so it complies with this rule like every other card — there is currently no live exception to Rule 12 for any component.
  - `/book-adventure`'s dark-bg wizard card had a `border-dark-border` override on top of `.card_base` (needed back when the class's own border was always black, invisible on a black card fill) — removed as dead weight now that `.card_base` has no border to override.
  - **Out of scope, left as-is:** small non-card UI chrome that happens to share the same `border-2 border-coal-black` house style — badges, pills, numbered step markers, color-swatch dots, a dialog-close button, `card_prompt`'s own icon circle — none of those are "the card container," they're chrome sitting *inside or beside* one. Also out of scope: a data table's own header-row underline and a stat-grid's inter-cell separators (Rule 4's carve-outs — structural, not a card boundary), and `ui_dropdown.astro`'s trigger/listbox borders, which are Rule 9's outlined-control style, not a card.

### Testimonial cards & grids — `section_testimonial_grid`

Any page that needs social proof — reviews, quotes, permissioned press/social mentions — uses `card_testimonial.astro` (`src/components/sections/`) inside the waterfall grid pattern below (named `section_testimonial_grid` in the naming system above — it's a `section_`, not a file, since the grid itself is a documented composition convention, not a single component): uniform accent-colored `card_testimonial`s throughout (one shared accent per Rule 14), with `card_prompt`/PromptCard breaking the grid at intervals in its own, deliberately contrasting accents. This is a standard page type, not a one-off: **`/reviews` is the reference implementation** — read its frontmatter (`src/pages/reviews.astro`) before building a new testimonial wall, especially for how it wires up `card_prompt`'s `PROMPT_CARD_ACCENTS`.

#### `card_testimonial.astro`

**For:** one testimonial/review as a card. Extracted from `/reviews`, which originally had two near-duplicate inline markup blocks (a "feature" card for permissioned quotes, a "review" card for platform reviews) — now one component with two variants.

**Props:** `name`, `sourceLabel` (e.g. `"LinkedIn · she is also a psychologist"` or `"bina parent · US · May 2024"`), `sourceLinkLabel` (e.g. `"Read it on LinkedIn"` / `"Verified on Trustpilot"`), `sourceLinkHref`, `logo` (image src), `logoAlt?`, `tint` (one accent — `grass`\|`yellow`\|`purple`\|`pink`\|`green`\|`blue`\|`red`\|`orange`), `title?`, `description` (plain text; `\n\n` splits into paragraphs in the dialog view), `rating?` (1–5, visual is always five filled stars — only the aria-label reflects the real number), `button?: { label?: string }`, plus a passthrough `class` and any `data-*` attribute onto the card root.

**Two variants, selected by the presence of `button`:**
- **Omitted** — a short, static blurb: name, source line, source link, optional title, description. No expand.
- **Passed (even `{}`)** — for a description that can run long. The description is CSS `line-clamp-3` (no fixed pixel/em height, no fade mask). On load, the component checks whether it actually got clipped (`scrollHeight > clientHeight`) — only then does a "See more…" button appear, opening a native `<dialog>` with the full untruncated text. A review that already fits in 3 lines never gets a button. Own scoped script, dedupes automatically across every card instance on the page (same pattern as `ui_accordion`).

**Card background:** always the section's single assigned accent (via the `tint` prop) — never white, never alpha-diluted, and **never varied per card**. Per Rule 14 (one accent color per section, applied everywhere within it), every `card_testimonial` in one grid takes the SAME `tint` — currently purple (`#b38cff`) on `/reviews`. The prop still accepts any of the 8 accents so the component stays reusable for a future page/section with a different single accent, but the caller is responsible for passing one consistent value across a whole grid, never a per-card mix. (`/reviews` used to vary `tint` per card and solve accent adjacency between neighbors offline — see this component's own doc comment in `card_testimonial.astro` for why that entire mechanism was removed: there's no adjacency to solve once nothing in the grid is adjacent-but-different.) Text is always black (Rule 2). The card has **no fixed height** — it sizes to whatever its own content needs; see the grid section below for why.

**Type sizes** (fixed for this component specifically, tuned by hand for a dense review-wall grid — though every value happens to land exactly on a step of bina's official type scale, see Rule 10's component-spec audit above): name 16px, source line 16px, source-link text 16px, description 18px, button text 16px — i.e. `Small` for everything except the description, which is `Body3`.

**Source icon:** the `logo` image is a **40px × 40px circle** (`h-10 w-10 rounded-full`) — not a rounded square. The underlying brand SVGs (`public/images/logos/*.svg`) are drawn on a small-radius rounded-square backing (`rx="4"` on a 48×48 viewBox); `rounded-full` on the `<img>` itself crops that into a circle regardless of the source file's own shape, so this is consistent across every source — LinkedIn, Instagram, Trustpilot, Niche, world-schools, thebinaschool.com — without needing per-source markup.

**Source-attribution link (both the compact card view and the "See more" dialog) renders through `<UiLink>`, not a hand-coded `<a>`** — this was a real, live bug (see `ui_link.astro`'s own catalog entry above for the full root-cause writeup) where both links kept their original hand-rolled markup through the entire sitewide link-migration task and had zero hover/focus CSS as a result. Card view: `<ui_link cardFill="accent">` (the card is always accent-filled, Rule 2 → black text) wrapping the label, the existing external-link SVG icon, and the `sr-only` "(opens in a new tab)" span together in one slot — `variant="inline"` (the default) so it inherits the surrounding `text-small` from its parent `<p>` rather than being forced to `ui_link`'s `standalone` 18px. Dialog view: `<ui_link cardFill="dark" accentColor={tint}>` (the dialog is a black card, Rule 1 → the section's own tint), same `inline` variant for the same sizing reason, with the trailing "→" kept as a literal character in the slot rather than `ui_link`'s own auto-arrow — since this text already inherits the correct size from its `text-small` parent, forcing `variant="standalone"` just to get the auto-arrow would also force the wrong 18px/`text-body-3` size. **Both instances need `!font-bold` (not plain `font-bold`) in their passthrough `class`** to win over `ui_link`'s own baked-in `font-semibold` for the `inline` variant — confirmed empirically (a plain `font-bold` passthrough class computed to 600, not 700, since Tailwind's cascade order for two same-property utility classes doesn't follow HTML attribute order); `!font-bold` forces it via `!important`, the same override technique `.ui_button_ghost`'s per-instance color overrides already use elsewhere in this repo.

**"See more" button — full spec:**
- 16px text, 700 weight, `Rund Display`
- `#000000` background
- `#ffe916` (lemon) text — **a deliberate, approved exception to the sitewide "no yellow text" brand rule** (see the Brand rule section's own note on this). Body/heading copy is never yellow; this is small button-label text on its own solid black chip, a different case, and the pairing was chosen specifically for this button. Do not "fix" it to black text or flag it in a future review.
- 12px border-radius
- Positioned bottom-**left** of the card (a corrected earlier bottom-right placement)
- **Normal document flow, never `position: absolute`** — sits `mt-4` (16px) below the description. An earlier version fixed every card to one height and absolutely-positioned the button over the description at a set offset; on a long review, the fade-truncation math didn't reliably keep the button clear of the last visible line, and the button overlapped live text. That's why the card has no fixed height and the button is in-flow — this is load-bearing, not cosmetic.
- **Content-width, left-aligned (`self-start` inside the card's `flex flex-col`) — the *content-width* case of Rule 25**, not a full-width button: sized to its own label, flush with the card's text column above it rather than centered in space it was never given.

#### `card_prompt.astro` — vs. `card_testimonial.astro`

**For:** a call-to-action prompt *embedded inside* a testimonial/review wall — e.g. `/reviews`' "Already a bina family? Write a review", "Reading about it only goes so far → Visit bina", "Stories are one thing. Scores are another → See the scores". This is not a review or a quote; it's the wall's own editorial voice breaking in. **Use `card_testimonial` for anything actually said by a family or press source; use `card_prompt` for anything the page itself is saying.** The two must look distinct, not just differently colored — before this component existed, these prompts were solid-accent-filled `<div>`s that looked like just another tinted testimonial card, which read as confusing (a reader could mistake bina's own prompt for something a family said).

**Also known as "PromptCard"** — the same component, that's just what the wall's own editorial-voice cards are called colloquially (they prompt an action, they aren't reviews).

**Props:** `icon` (`'star' | 'eye' | 'chart'`), `heading`, `body` (one line — no title/description split, no multi-paragraph), `buttonLabel`, `buttonHref`, `accentColor` (one of the 7 non-yellow accents), plus a passthrough `class`. The component also exports `PROMPT_CARD_ACCENTS: Props['accentColor'][]` — see the assignment rule below.

**What makes it read as a different kind of card, deliberately, point by point:**
- **Solid `accentColor` fill** (`bg-bina-*`, via the `accentColor` prop) — filled, not black. An earlier version used a black background with an accent border to read as distinct from the (then multi-tint) testimonial grid; now that `card_testimonial`s are all one uniform accent (see that component's spec above), `card_prompt` differentiates itself by using an accent the grid itself isn't using (see "Accent assignment" below), not by a different fill treatment.
- **No border** — plain `.card_base`-style filled card, Rule 12 compliant like every other card sitewide. (This component briefly carried a 2px accent border for one pass, when the black-background version needed it to stand out; removed once the card moved to a filled-accent look.)
- **All text — heading and body — is `#000000`**, per Rule 2 (text on an accent-filled card is always black).
- **An icon in a small OUTLINED circle at the top** — transparent fill, 2px `#000000` stroke, with an outline-style icon glyph (not a filled circle with a solid icon knocked out of it) — replacing the avatar-image + name/source row entirely. There is no name, no source, no rating, no attribution metadata of any kind on this card, because it isn't attributed to anyone.
- **One heading + one line of body text only** — no title/description split, no dialog, no "See more" expand. If the copy needs more than a line, it's too long for this component.
- **A full-width primary `.ui_button`** (the standard CTA button, see "Standard CTA button" above) instead of `card_testimonial`'s small bottom-left "See more" chip — this card's whole point is the button, so it gets the site's actual primary-action treatment, not a secondary affordance. The button keeps its standard yellow fill regardless of the card's own accent — see the note on yellow-vs-accent contrast below. **Full-width, centered label (`w-full text-center`) — the *full-width* case of Rule 25**, not a Rule 13 violation: the button spans the card's whole content width, so there's no competing left edge for the label to align against.

**Accent assignment — the deliberate exception to Rule 14.** Every `card_testimonial` in a grid shares the section's one accent (see that component's spec above), but `card_prompt` is exempt from that: its whole job is to stand out from the uniform testimonial grid around it, so each `card_prompt` in a grid instead gets its own accent, assigned explicitly, in SOURCE ORDER, from `card_prompt.astro`'s own exported `PROMPT_CARD_ACCENTS` list (currently `['orange', 'grass', 'blue', 'purple', 'pink', 'red', 'green']`). This is **never** randomized at build time — the page must render identically on every build — and no two `card_prompt`s in the same grid may share an accent. **A `card_prompt` also may never use the section's own accent** (currently purple on `/reviews`) — since the card's whole differentiator is now its fill color (not a black-vs-accent treatment), reusing the section accent would make it disappear back into the grid it's meant to interrupt. The calling page filters that color out of `PROMPT_CARD_ACCENTS` before assigning — see `/reviews`' own `availablePromptAccents` for the reference pattern. If a page ever needs more `card_prompt`s in one grid than colors remain after that filter, that's a build-time error to surface, not a color to silently repeat — see `/reviews`' own overflow check. This is a much simpler rule than the old per-card adjacency solve `card_testimonial` used to need (see the grid section below) — `card_prompt`s are sparse in the wall, not dense enough for the same touching-neighbor problem, so a plain ordered list is sufficient.

**Yellow button vs. accent-filled card — checked, no change needed.** `.ui_button`'s yellow fill (`#f7d928`) sits on top of every `accentColor` this component can take. Measured by WCAG relative-luminance contrast (fill-to-fill, not text contrast), every pairing is weak — grass (`#03ecc5`) is the tightest at roughly 1.1:1, purple (`#b38cff`) next at roughly 1.8:1, the rest cluster around 1.5–2.2:1 — because this whole accent palette (yellow included) is deliberately mid-to-high luminance, so luminance alone barely separates any two of them. What actually keeps the button legible on every card is `.ui_button`'s own built-in 2px solid `#000000` border (part of the standard button spec, unrelated to this component) — a hard boundary line satisfies the same purpose luminance contrast would, independent of which accent the card underneath happens to be. So: no card-specific button treatment is needed and none was added; if a future accent is ever added to the palette, sanity-check its luminance against yellow the same way, but don't expect any pairing to clear a clean 3:1 on fill alone — the border is what's actually load-bearing here, by design.

**Grid participation:** runs in the exact same `columns-*` waterfall as `card_testimonial` — `mb-4` + `break-inside-avoid` are baked into its root the same way, so it can be mixed freely into the same grid without the caller doing anything extra.

#### The grid — waterfall, not uniform rows

**Layout:** CSS multi-column (`columns-*`), never a `grid`. A uniform-row `grid` was tried and rejected — even with `items-start`, Grid sets a row's height to its *tallest* card across every column, so a short card sitting in the same row as a tall neighbor gets extra dead space before its own next card starts: the vertical gap between two stacked cards in one column becomes inconsistent, purely because of what some *other* column happened to contain. A `columns-*` container instead flows each column's cards independently top-to-bottom, so the gap is always exactly what the component sets, never dependent on any other column.

**Container:** `columns-1 gap-4 md:columns-2 xl:columns-3 2xl:columns-4` (the column-count progression can be tuned to a new page's density, but keep the responsive-columns approach, not `grid`). Every card carries `mb-4` (16px) and `break-inside-avoid`, **baked into `card_testimonial.astro`'s own root class list** — not left to the caller to remember. `gap-4` (16px) on the container gives the matching horizontal gap between columns (`gap` is a valid CSS property for multi-column layout, not only grid/flex).

**Gap is 16px in every direction** — vertical (stacked, same column) and horizontal (column-to-column) both, one consistent value. Do not add a fixed height back to `card_testimonial`, its container, or a wrapper class like the old `.wall-cell` — that's the exact thing this pattern was built to avoid.

**No adjacency rule for `card_testimonial`s.** Every `card_testimonial` in a grid shares the section's one accent (Rule 14 — see that component's spec above), so there is nothing to solve for adjacency: touching cards are *supposed* to share a color now. This replaces an earlier version of this pattern, where each card carried its own tint and a graph-coloring solve (offline, against real rendered adjacency at the 2/3/4-column breakpoints) ensured no two touching cards matched — that entire mechanism, and the `REVIEW_TINTS`-style array it produced, is gone. `card_prompt`/PromptCard still needs its own accents kept distinct from *each other* (not from the testimonial cards around it) — see that component's own "Accent assignment" spec above for the current, much simpler source-order mechanism.

## 🔴 Data visualisation & charts

### Data-visualization components — the standard set

Every stat/data page (`/family-survey`, `/student-results`, `/esa/[state]`) was independently hand-rolling the same handful of shapes: a labeled section wrapping a card, a circular progress ring, a row of horizontal bars, a single bar split into categories, vertical bars off a baseline, a styled table. These are now components, all in `src/components/sections/`. **`/family-survey`, `/student-results` and `/esa/[state]` are the reference implementations** — read their frontmatter before building a new stat page.

**One exception, deliberately not componentized:** the bell-curve / distribution chart (`/student-results`' "the whole school moved forward" section — a Gaussian-path SVG built from a mean/SD pair, with its own scroll-reveal and an inline "see the numbers" table) stays page-specific custom SVG. It's the one shape that doesn't recur anywhere else, and the math (`gaussianPath()`) is bespoke enough that extracting it now would be speculative — componentize it if and when a second page actually needs a distribution curve. **Card background and text color were still edited in place for Rule 18** (its two curve colors — Oct '25 blue, May '26 green — are exactly the multi-color-on-an-accent-card pattern Rule 18 exists to catch): the card moved from `bg-bina-pink` to `bg-coal-black`, and every text element inside it (title, growth figure, legend, axis/baseline lines, the `.chart-label` SVG text, the "See the numbers" table and its borders) moved from black to the section's pink accent (`#fe48c2`/`text-bina-pink`). The two curve fills themselves, and their own black outline strokes, are untouched — this is a recoloring of the card's chrome, not the "leave the component alone" guidance above being reopened, which was specifically about *not* wiring its stroke-width to the shared `--stroke-chart` token (still true) — a different, narrower thing than this card-level color fix.

#### `layout_stat_section.astro` — the shell

**For:** the "eyebrow label + h2 + intro paragraph + card" wrapper repeated by hand across every stat section before this existed. Confirmed duplicated, not shared, before this pass — every page independently wrote its own `<section class="bg-dark-bg"><div class="mx-auto max-w-6xl px-8 py-[clamp(3rem,6vw,6rem)]">…</div></section>` plus the eyebrow/h2/intro markup inline.

**Props:** `heading` (string), `accentColor`, `eyebrow?` (the small uppercase label above the h2, e.g. "Time with bina"), `introClass?` (default `max-w-2xl`), `id?`, `class?`. Default slot is the card/chart content; named `intro` slot is the optional paragraph between heading and card (only rendered if used — omit it entirely when a section has no separate intro, e.g. because the intro text lives *inside* the card itself instead, per Rule 2's black-text convention — see `/family-survey`'s donut and dimension-bar sections for that pattern).

**Bakes in Rule 11 and Rule 13 by construction** — the standard `max-w-6xl px-8` container, left-aligned by default, and a guaranteed 32px+ gap from heading/intro down to the card slot — so a new section built on this shell can't accidentally reintroduce either violation.

**Scoped to ordinary `<h2>` content sections, not heroes** — a hero mixes in an `<h1>`, `pill_label`, CTA buttons, sometimes a gate-checklist; different enough per page that forcing it through one shell would fight more than it'd save. Keep writing heroes by hand.

#### `card_stat.astro` — one stat in a grid

**For:** a single small stat meant to be repeated in a grid — `/student-results`' headline stats, `/esa/[state]`'s proof and money stat grids. For **one** prominent stat living inside a card the page already provides (not its own grid card), use `chart_donut` (`variant="number"`) instead.

**Props:** `value` (pre-formatted string, e.g. `"$8,200"`) or `count` (a plain number — animates counting up from 0 on scroll-into-view; use `countPrefix`/`countSuffix` for a `+`/`%` around it), `label`, `note?` (plain string, or use the `note` named slot when it needs a link — e.g. "12 reviews · read all of them"), `accentColor`, `fill?` (`'accent'` default — `card_base bg-bina-{accentColor}`, black text per Rule 2; or `'dark'` — `bg-coal-black`, `accentColor` text per Rule 1, for a result panel sitting on the page's own dark background rather than an accent fill), `valueSize?` (`'lg'` default = `text-5xl`, `'md'` = `text-3xl` for denser grids), `labelColor?` (`fill="dark"` only — `'accent'` default keeps `label`/`note` in `accentColor`; `'muted'` switches them to `--color-muted-gray` per Rule 24, e.g. `/esa/[state]`'s hero fact cards, where the value is the section's claim but the sentence under it is supporting detail, not the message).

**Self-contained count-up** — its own `IntersectionObserver`, scoped to `.stat-card[data-count]`, dedupes automatically across every instance on a page (same pattern as `card_testimonial`'s "See more" button). The calling page needs no script of its own for this — migrating `/student-results` and `/esa/[state]` to `card_stat` let each page delete its own hand-rolled count-up `<script>` entirely.

**`label` and `note` are both `text-xl`** (20px, Rule 10's default reading tier) — they were unstyled/`text-base` originally and silently inherited the wrong size; see Rule 10's own writeup on this exact gap.

#### `chart_donut.astro` — one headline stat

**For:** the ONE number a section is built around, sitting inside a card the page already provides. `variant="ring"` (default) is a circular progress ring filling to `value / max`, extracted from `/family-survey`'s recommendation donut. `variant="number"` skips the ring for a bare big centered number (`/family-survey`'s "70% of families…" stat) — set `countUp` to animate it.

**Props:** `variant?`, `value`, `max?` (default 10), `unit?`, `fillColor?` (ring variant only — see below), `ariaLabel?`, `countUp?`, `countDecimals?`, `cardFill?: 'accent' | 'dark'` (ring variant only, default `'dark'`), `accentColor?` (required when `cardFill="dark"`).

**A ring is its own accent-colored mark, so per Rule 18 it never sits on an accent-filled card** — `cardFill="dark"` (the live default) puts it on `bg-coal-black`, with `fillColor` set to the section's own accent (Rule 18's black-card fill case, not a Rule 7 cross-accent pairing) and `.donut-value`/`.donut-unit` switched from black to `accentColor` (Rule 1). `cardFill="accent"` is kept only for a hypothetical, deliberately-reviewed future exception — don't reach for it by default. `variant="number"` has no ring at all (a bare number, no additional accent-colored mark), so it's outside Rule 18 entirely and keeps whatever accent-card treatment the caller's `class` gives it, unaffected by `cardFill`/`accentColor`. Ring sweeps in from empty on scroll-into-view (CSS transition, `prefers-reduced-motion` respected); self-contained via its own `IntersectionObserver` scoped to `.donut-stat`.

#### `chart_bar_list.astro` — several scores against a shared max

**For:** multiple scores/values measured against the *same* max, stacked as full-width horizontal bars — `/family-survey`'s seven-dimension rating chart is the reference. **Use this, not `chart_segmented_bar`, when the values are independent scores** (several ratings out of the same 10) rather than a breakdown that sums to 100%.

**Props:** `items: {label, value}[]`, `max`, `unit?` (e.g. `"/10"`), `fillColor` (a single hex — Rule 14, one accent per section), `referenceLine?: {value, label}` (a dashed marker, e.g. "8/10"), `animate?` (default true — bars grow in from the left on scroll-into-view, self-contained), `cardFill?: 'accent' | 'dark'` (default `'dark'`), `accentColor?` (required when `cardFill="dark"`).

**Every bar's fill is its own accent-colored mark, so per Rule 18 this chart never sits on an accent-filled card** — `cardFill="dark"` (the live default) puts it on `bg-coal-black`, with `fillColor` set to the section's own accent (Rule 18's black-card fill case, not a Rule 7 cross-accent pairing) and every text element (value labels, axis "0"/`max`, the reference-line label), the unfilled track, and the axis/reference lines switched from black to `accentColor` (Rule 1). `cardFill="accent"` is kept only for a hypothetical, deliberately-reviewed future exception.

**Honest axis, always** — the track runs the full `0` to `max`, never a cropped baseline (per the "Publishing our own data" rules) — put the weakest score in the same chart as the best.

**Same two fixes as `chart_vertical_bar`, same reasoning — both apply here too:**
- **Axis end-labels never collide with the axis line.** The margin reserved below the axis line for the "0"/max labels is a fixed 26 viewBox units regardless of whether `referenceLine` is set — it used to collapse to 6 units when `referenceLine` was omitted, which put those labels at the *exact same y-coordinate* as the axis line itself. Not visible on `/family-survey` (its usage always passes a `referenceLine`, which happened to avoid it) until it was checked directly — any future no-`referenceLine` usage would have hit it.
- **Every text class declares a real, literal `font-size: 18px` — never a smaller number chosen to counteract this SVG's own scale.** This SVG is `w-full` inside the standard content card (~1072px at desktop, in a 700-unit viewBox — roughly a 1.53× scale), so a literal `18px` renders at ~27.6px on screen for every class, row labels and values alike. A version of this component briefly declared `.pbl-label-sm` (row labels, axis "0"/max end-labels) as `font-size: 12px` specifically to land closer to a *true* 18px on screen — that's a real violation of Rule 10's 16px floor (a sitewide rule with no carve-out for "but it's inside a scaled SVG"), and it had already been fixed once before in this exact class (see Rule 10's own history). Row/value hierarchy comes from weight and typeface (`.pbl-label` is bold `Rund Display`, `.pbl-label-sm` is regular `Rund Text`), not from a font-size gap — don't reintroduce a sub-16px declaration to manufacture one.

#### `chart_segmented_bar.astro` — one breakdown that sums to 100%

**For:** a single bar split into colored segments that sum to 100%, with a legend underneath — `/family-survey`'s "what matters to them" priorities breakdown is the reference. **Use `chart_bar_list` instead** when the values are independent scores rather than one physical bar's worth of categories.

**Props:** `segments: {label, pct, color}[]`, `width?` (default 640), `caption?`, `cardFill?: 'accent' | 'dark'` (default `'accent'`), `accentColor?` (required when `cardFill="dark"`).

**Always multi-color by construction** (each segment is its own category color), so per **Rule 18** the card it sits inside must be black, not accent-filled — `cardFill="dark"` switches the legend/caption text from Rule 2's black to Rule 1's section-accent color (via `accentColor`) to match. The `'accent'` default only exists for backwards compatibility and shouldn't be reached for on a real multi-color breakdown; `/family-survey`'s usage passes `cardFill="dark" accentColor="orange"` on a `bg-coal-black` card. The bar's own outline stroke and internal segment dividers stay literal black regardless of `cardFill` (Rule 7 — the stroke requirement is unchanged in both cases).

**Corner radius and stroke follow the shared bar-chart spec (CLAUDE.md's Rule 7 addendum)** — only the two outer ends round (via a clip-path, since a plain rect's `rx` would round internal seams too), one shared `stroke-width="2"` outline wraps the whole bar, and thin 2px dividers mark internal seams only, never a full per-segment border (which would double the seam thickness — the exact bug this component's extraction fixed). Each segment's `color` is its own category color, not a Rule 7 fill pairing — this isn't a progress-fill-on-a-card-background situation, it's several categories that need to read as visually distinct from each other.

#### `chart_vertical_bar.astro` — bars off a baseline

**For:** "how far above/below a baseline does each group sit" — `/student-results`' tenure chart ("the longer at bina, the further ahead in reading") is the reference. The baseline is a true-zero reference line the caller labels (e.g. "national average reading level"), not a cropped axis.

**Props:** `bars: {label, value, title?}[]`, `baselineLabel`, `fillColor` (single hex, Rule 14), `valuePrefix?` (e.g. `"+"`), `hoverColor?` (a fixed hover fill, independent of `fillColor` — `/student-results`' bars hover to a fixed orange regardless of card color, preserved as an explicit prop rather than invented as a formula), `cardFill?: 'accent' | 'dark'` (default `'dark'`), `accentColor?` (required when `cardFill="dark"`).

**Every bar's fill is its own accent-colored mark, so per Rule 18 this chart never sits on an accent-filled card** — `cardFill="dark"` (the live default) puts it on `bg-coal-black`, with `fillColor` set to the section's own accent (Rule 18's black-card fill case, not a Rule 7 cross-accent pairing) and the baseline line plus every text label switched from black to `accentColor` (Rule 1). `hoverColor` is untouched by `cardFill` — it's a transient, one-bar-at-a-time interaction state, never simultaneously visible alongside the resting fill, so it doesn't count as a second persistent accent under Rule 18 and stays whatever fixed color the caller wants. `cardFill="accent"` is kept only for a hypothetical, deliberately-reviewed future exception.

**No scroll-reveal animation** — the source chart this was extracted from didn't have one, so none was added on migration, to avoid a visual change nobody asked for. Add one later if a page actually wants it.

**Bars sit 4 viewBox units above the baseline, never touching it** — a bar drawn flush against the baseline visually merges into it and reads as one shape instead of two separate elements. The baseline itself doesn't move to make room for this; only the bars are offset upward, so the axis stays exactly where the caller/reader expects it and only the data shifts.

**Every text class declares a real, literal `font-size: 18px` — never a smaller number chosen to counteract this SVG's own scale.** This SVG is `w-full` inside the site's standard content card (~1072px at desktop, in a 640-unit viewBox — roughly a 1.675× scale), so a literal `18px` renders at ~30px on screen for every class, category labels and values alike. A version of this component briefly declared `.vbc-label-sm` (category labels, the axis caption) as `font-size: 11px` specifically to land closer to a *true* 18px on screen — that's a real violation of Rule 10's 16px floor (a sitewide rule with no carve-out for "but it's inside a scaled SVG"), and it had already been fixed once before in this exact class (see Rule 10's own history). Value/category hierarchy comes from weight and typeface (`.vbc-label` is bold `Rund Display`, `.vbc-label-sm` is regular `Rund Text`), not from a font-size gap — don't reintroduce a sub-16px declaration to manufacture one.

**Axis captions and category labels must never overlap each other.** The axis caption sits on its own line directly below the baseline; the category-label row sits far enough below the caption that the two rows never collide, even accounting for real letter descenders — this was a real, reported bug (the caption and the first category label were rendering close enough to touch) before the vertical spacing and the font-size fix above were both corrected together.

#### `chart_table.astro` — a table on an accent card

**For:** a plain data table styled for sitting inside an accent-colored card — `/family-survey`'s exam-preparation table is the reference. Header row gets a solid 2px underline; body rows get a faint 15%-opacity divider between them — **the one place a divider-within-a-card is structural rather than decorative**, Rule 4's own carve-out for a table's row lines, not a violation of "no dividers inside cards."

**Props:** `columns: string[]`, `rows: (string|number)[][]`, `boldColumns?` (default: first and last column — matches the source table's own emphasis pattern).

#### `chart_ranked_list.astro` — a sorted breakdown

**For:** a ranked list of items, each with a value and a proportional inline bar, read top-to-bottom by rank rather than compared as one continuous shape — a "top reasons families chose bina" or "which platform sent the most reviews" breakdown. **Use `chart_segmented_bar`** when the categories sum to 100% and read as one physical bar; use this when they're independent figures best read as a sorted list.

**Props:** `items: {label, value, note?}[]`, `max?` (defaults to the largest value, so the top row always reads full-width), `unit?`, `fillColor`.

**Not yet adopted by any page** — built alongside the rest of this set per the reusable-chart-set brief ahead of an actual use case. `/family-survey`'s "the plan, ranked by what families asked for" wishlist card is a plausible future adopter (same "ranked, with a value" shape) but wasn't migrated to it this pass, since its current markup (border-divided rows, no inline bar) is visually different enough that switching would be a real appearance change, not a like-for-like refactor.

- **Rule 7 — progress bar / donut fill colors: two cases, by card background.**
  - **Fill on an accent-colored card** — documented for completeness; per Rule 18's corrected reading, this case has **no live usage anywhere on the site** (every chart with its own fill now lives on a black card instead). Kept here only in case a future, deliberately-reviewed exception ever needs it. Fill colors, when this case is invoked, are **not computed** from a rule (color temperature, hue distance, contrast ratio, or anything else) — that was tried and failed visual review. They follow this fixed, pre-approved lookup table only, matched by card background:

  | Card background | Approved fill |
  |---|---|
  | Lila / light purple `#e2ccff` | Watermelon red `#ff6d63` |
  | Lemon `#ffe916` | Magenta `#fe49c1` |
  | Magenta `#fe49c1` (≈ `bina-pink`) | Turquoise `#2fe5c9` |
  | Watermelon red `#ff6d63` (≈ `bina-red`) | Turquoise `#2fe5c9` |
  | Orange `#ff6a00` (≈ `bina-orange`) | Grass green `#43ca66` |
  | Purple `#b38cff` (= `bina-purple`) | Grass green `#43ca66` |
  | Grass green `#43ca66` (≈ `bina-green`) | Magenta `#fe49c1` |
  | Light blue `#4f97fc` (≈ `bina-blue`) | Orange `#ff6a00` |
  | Turquoise `#2fe5c9` (≈ `bina-grass`) | Purple `#b38cff` |

    Never use a fill color outside this table for a given card background. If a new accent color is ever added to the palette, a new approved pairing must be chosen deliberately through visual review and added here — never inferred from a rule or formula. Apply the fill as the exact hex in this table, not the nearest `bina-*` Tailwind class — the approved pairing is the literal color, not "whichever accent is roughly that hue."
  - **Fill on a black card (Rule 18)** — no pairing table needed here: the fill IS the section's accent color, single-accent, matching the section (Rule 14/Rule 1). The card's own black background is what creates the contrast, not a second, different accent chosen to pair against it. E.g. a black card in an orange section (per Rule 18) uses `#fe6c23` (orange) for its bar/donut/column fills, the same orange as the section's heading and body text — never a different accent picked for contrast the way the accent-card table does.
  - **Stroke requirement — unchanged, applies in both cases above:** every progress bar / donut fill segment gets a solid black (`#000000`) stroke/border outlining it, regardless of card or fill color. The black stroke must fully enclose the fill segment, including its start and end edges, not only the outer and inner arcs. For a stroke-drawn ring (not a filled shape), a plain wider-circle-underneath trick only borders the long curved edges and leaves the two cut ends bare — use `stroke-linecap="round"` (or another cap that closes the end) on both the black and colored strokes so the outline wraps the whole pill-shaped segment, ends included.
  **Corner radius and stroke weight are shared across every bar-style data visualization on the site — progress bars, donuts, segmented/split bars, and vertical bar charts alike: `rx="6"` and `stroke-width="2"`, `stroke="#000"`.** This is one visual language, not a per-chart-type choice — a reader shouldn't be able to tell from corner rounding alone which chart component they're looking at. **The `2` isn't its own arbitrary number — it's the same stroke weight as `.ui_button`'s own border (`border-2`, 2px), the site's one other black-outline-on-a-colored-fill pattern.** Tokenized as `--stroke-chart` in `global.css` (see its own comment there for why it's a plain reference value, not a Tailwind-generating token) — apply it via `style="stroke-width: var(--stroke-chart)"` on the element (or a shared CSS class in the component's own `<style>` block), never a repeated literal `2`. **Scope is the black stroke that outlines a colored fill segment specifically** — an axis line, baseline, or dashed reference-line marker (e.g. `chart_bar_list`'s `0`–`max` axis, `chart_vertical_bar`'s baseline) is a different design element that happens to often share the same numeral; those are left as literal values, not wired to this token, since they aren't "a fill's own outline" and changing them isn't what this rule governs. `chart_donut`'s ring is a special case: its "black stroke" isn't a standalone `stroke-width="2"` at all — it's a wider black arc (`stroke-width="26"`) drawn underneath the colored arc (`stroke-width="22"`), so 2 units of black peek out on each edge; `26 = 22 + 2 × 2`, tied to the same value in spirit but expressed as arithmetic Astro's frontmatter has to compute at build time (a CSS custom property isn't readable there), so it can't literally reference `var(--stroke-chart)` — if the shared value ever changes, this one has to be updated by hand alongside it. chart_donut's two faint boundary hairlines (the `r="100"`/`r="78"` circles at 20% opacity) aren't part of that arc technique and do reference the token directly. **The one deliberate exclusion:** `/student-results`' bell-curve distribution chart (see "Data-visualization components" below) already draws its own black outline strokes at `stroke-width="2"`, matching this value, but is intentionally *not* wired to the token — it's explicitly out of the componentized/tokenized chart set (bespoke, page-specific SVG, not one of the four reusable chart types this rule governs), and pulling it in would mean touching a component CLAUDE.md itself says to leave alone until a second page needs the same shape. For a **single-fill progress bar** (one dimension, one score — e.g. `/family-survey`'s "Communication / feeling…" rows and `/student-results`' growth bars), apply `rx`/`stroke-width` directly to the one `<rect>`. For a **segmented/split bar** — several colored fills concatenated into one continuous bar, no gaps, summing to 100% (e.g. `/family-survey`'s "32% Creativity & critical thinking…" four-way split) — do **not** put `rx` on each individual segment `<rect>`: since SVG rounds all four corners of a rect uniformly, that would round the internal seams between colors too, which reads as broken/notched rather than as one bar. Instead, clip the plain square-cornered segment fills to a single `rx="6"` `<clipPath>` sized to the whole bar so only the two outer ends round, then draw one `rx="6"` `stroke-width="2"` outline `<rect>` over the top for the shared border — segment-to-segment seams stay straight, matching how a physical segmented bar/pill actually looks. **Never put a stroke on the individual segment `<rect>`s themselves** — every segment sharing one continuous edge with its neighbor means two adjacent strokes stack into a doubled-thickness seam (visibly heavier than the bar's own single-thickness outer stroke), which is exactly what this pattern is meant to avoid. If segment boundaries should read visually (they usually should, for a 3+ way split), add a single **1–2px solid black divider `<rect>`** at each internal boundary — inside the same clipped `<g>`, positioned only between segments, never at the two outer ends (those already get the container's own rounded stroke). `/family-survey`'s "what matters to them" chart is the reference implementation for this pattern.
- **Rule 18 — no accent color may sit on top of another accent color, full stop. A card is black whenever its content carries ANY accent-colored mark of its own — a chart fill, a ring, a bar, a column — not only when that content is multi-color.** The literal test is: does this card have an accent-colored graphic element that is a *different* color from the card's own fill? If yes — even exactly ONE such element — the card must be black (`#000000`), never accent-filled, with its heading and body text in the section's accent color (Rule 1, not Rule 2 — see Rule 6's amendment above). "Multi-color" was this rule's original trigger case (a bell curve, a segmented bar), but the underlying principle was never about *counting colors* — one extra accent stacked on a different accent card is exactly as much a violation as four.
  - **Corrected mid-pass, worth recording so it isn't repeated:** an earlier version of this rule carved out "single-accent" content — a `chart_donut` ring, a `chart_bar_list`/`chart_vertical_bar` fill — as compliant to leave on an accent card, reasoning that Rule 7's existing cross-accent pairing table (e.g. a purple card with a green fill) was pre-approved, unchanged behavior. That was wrong: a single Rule-7-paired fill is still one accent color sitting on a *different* accent-colored card — the exact stacking this rule exists to ban, just with a lookup table sanctioning which specific pairs happened to look acceptable together. Being "only one extra color" was never the exemption; having *zero* extra accent-colored marks is. **Three real instances were missed under the old reading and are now fixed** (see below); this doc note exists so a future single-fill chart isn't waved through the same way.
  - **What's actually exempt: text-only content, or content whose only color IS the card's own accent (nothing added).** A `card_stat` (number + label, no chart), a `chart_table` (plain text cells), and `chart_donut variant="number"` (a bare number, no ring) have no additional accent-colored graphic element at all, so they're outside this rule entirely and keep the accent-colored card per Rule 6. This is a narrower exemption than "single fill color" — the moment a chart draws its own colored mark (ring, bar, column, segment) in a color distinct from the card, Rule 18 applies, regardless of how many distinct colors that mark uses.
  - **Fill colors on a Rule 18 black card follow Rule 7's second case:** the fill IS the section's own accent color — single-accent, matching the section (Rule 14) — not a Rule 7-table pairing. **In practice this means Rule 7's accent-card pairing table (its first case) now has no live usage anywhere on the site** — every chart component that draws its own fill moves to a black card under this corrected reading. The table stays documented (a future, deliberately-reviewed exception could still invoke it), but treat it as dormant, not as grounds to leave a chart's own card accent-filled. The black stroke requirement (Rule 7) is unchanged in both cases.
  - **A `hoverColor` (e.g. `chart_vertical_bar`) is not a second persistent accent and doesn't trigger this rule** — it's a transient interaction-state swap, never simultaneously visible alongside the resting fill (one bar at a time, on pointer-over, replacing not adding a color). Left as its own fixed prop, independent of the card's fill mode.
  - **Fixed this pass — five real violations across two waves:**
    - **Wave 1 (genuinely multi-color content):** `/student-results`' bell-curve distribution chart (two curve colors on a `bg-bina-pink` card) and `/family-survey`'s "what matters to them" `chart_segmented_bar` (four category colors on a `bg-bina-orange` card) — both moved to `bg-coal-black`, with every text element switched to the section accent (`text-bina-pink` / `text-bina-orange`). `chart_segmented_bar` gained a `cardFill`/`accentColor` prop pair for its legend/caption text. Chart fills and their black outline strokes untouched in both.
    - **Wave 2 (single-fill charts, missed the first time — the corrected reading above):** `/family-survey`'s "How many parents recommend bina" `chart_donut` (magenta ring on a `bg-bina-green` card) and "how it feels to be here" `chart_bar_list` (green fill on a `bg-bina-purple` card), and `/student-results`' tenure-chart `chart_vertical_bar` (green fill on a `bg-bina-purple` card) — all three moved to `bg-coal-black`, with `fillColor` changed from its old Rule-7-paired hex to the section's own accent hex (green `#03cb5b` / purple `#b38cff` respectively), and all surrounding text (paragraphs, figcaptions) switched to the matching `text-bina-*` class. `chart_donut`, `chart_bar_list`, and `chart_vertical_bar` each gained the same `cardFill`/`accentColor` prop pair as `chart_segmented_bar` (default `cardFill="dark"`) so their own labels/axes/tracks render in the section accent instead of hardcoded black — see each component's own catalog entry.
  - **Audited, confirmed exempt, no change made:** `card_stat` (every instance, every page — text-only), `chart_table` (`/family-survey`'s exam table — text-only), `chart_ranked_list` (not yet adopted by any page). `/esa`, `/esa/[state]`, `/reviews`, and `/book-adventure` have no chart/data-viz components and no hand-rolled multi-color SVG at all, so nothing on those pages was in scope for this rule.
- **Rule 20 — multi-series chart colors: the first series takes the section's own accent, every additional series takes a contrasting color from the approved 8-accent palette — never an off-palette default.** Where a chart shows two or more data series at once (e.g. two distribution curves for two points in time, a legend distinguishing categories), the FIRST series uses the section's own accent color — the same color as the section's heading/text and every other single-accent element in it. Additional series use a different, contrasting `bina-*` accent — never a default charting-library color (a stock blue, a stock gray) that isn't actually one of this site's 8 accents. **This is a documented, deliberate exception to Rule 14** (one accent color per section, applied everywhere within it): Rule 14 is about a section having one color *identity*; a multi-series chart is different because color is doing *data* work there — distinguishing series from each other — not section branding, so more than one accent is allowed *within that one chart specifically*. It does not license a second accent anywhere else in the section — headings, card fill/text, and every single-fill chart type still follow Rule 14 exactly as before; this exception is scoped to the chart's own series colors only.
  - **Every series color must be one of the 8 approved `bina-*` accents** (expressed as the literal swatch hex, per Rule 7's own convention for chart fills, not necessarily the Tailwind class hex) — never an arbitrary or chart-library-default hex chosen because it "looks nice" against the other series.
  - **Fixed this pass:** `/student-results`' bell-curve chart ("The whole school moved forward," section accent pink) had its Oct '25 series in `#33afff` (bina-blue) — itself one of the 8 approved accents, so not literally off-palette, but not following this rule's ordering convention either (blue has no relationship to the section's own pink). Changed to `#fe49c1` (magenta, the literal swatch hex for the section's own pink-family accent, matching Rule 7's fill-hex convention) — the legend dot updated to match via an inline `style="background:#fe49c1"` (an exact-hex swatch, same pattern `chart_segmented_bar`/`chart_ranked_list` already use for their own category-color dots). May '26 stays `#03cb5b` (grass green) as the contrasting second series, unchanged.
- **Rule 21 — overlapping data series get semi-transparent fills, never solid ones.** When two or more chart series' fill areas can visually overlap (e.g. two bell curves sharing an x-range), each series' fill uses `fill-opacity` — not a full-opacity solid fill — so the overlapping region blends both colors and stays legible, instead of one series' solid fill fully hiding the other wherever they cross.
  - **Reference implementation:** `/student-results`' bell-curve chart — Oct '25 fill at `fill-opacity="0.3"`, May '26 fill at `fill-opacity="0.4"` (deliberately a touch higher, so the more recent series reads as the "foreground" curve in the overlap). Confirmed correct on review and kept as-is — this is the standard technique going forward for any new overlapping-series chart, not a one-off.
  - **The stroke stays fully opaque black regardless** (Rule 7's stroke requirement, unaffected by this rule) — opacity applies to the fill only, never the outline, so each series' own boundary stays crisp even inside the overlap region.
  - **Scope:** this only applies where series can actually overlap. The single-series bar/donut/column fills governed by Rule 7 are always fully opaque solid fills — they never share space with another series, so there's no legibility problem for opacity to solve, and adding it there would just wash out the color for no reason.

### Standard CTA button — `.ui_button`

`.ui_button` (defined in `global.css` `@layer components`) is **the single button style for every primary call-to-action on this site** — "Visit bina", "Book a call", "Start your bina journey", "Register interest", form-step "Continue" buttons, anything that is the main action a reader can take. Don't invent a one-off button style or hand-roll `rounded-* border-2 bg-bina-yellow …` classes on an element instead of using this class.

**Source:** extracted exactly from thebinaschool.com's own shared button (`Bina-School-R-D/website`, `src/components/ui/CTAButton.tsx`), specifically the `size="medium"` variant — the one used in every nav on the source site, matching this repo's own nav CTA. Re-extract from there if the source's button styling changes.

**Exact spec (all fluid `clamp()`, not flat Tailwind steps — it scales continuously with viewport, not in breakpoint jumps):**

| Property | Value |
|---|---|
| Background | `#f7d928` (`bg-bina-yellow`) |
| Text color | `#000000` (`text-coal-black`) |
| Hover background | `#fe48c2` (`bg-bina-pink`) |
| Active/press background | `#ff605b` (`bg-bina-red`) |
| Border | `2px solid #000000` |
| Border radius | `clamp(0.625rem, 0.83vw, 1rem)` — 10px → 16px |
| Padding | `clamp(1rem, 1.39vw, 1.5rem)` horizontal, `clamp(0.5rem, 0.7vw, 0.75rem)` vertical |
| Gap (label to icon, if any) | `clamp(0.375rem, 0.46vw, 0.5rem)` |
| Min-height | `clamp(2.45rem, 3.24vw, 5.25rem)` |
| Font | `font-display` (Rund Display), `text-button` token, **weight 400 — not bold.** The source sets `fontWeight: 400` explicitly; this repo's button briefly drifted to `font-bold` before being corrected here — don't reintroduce bold. |

**Secondary/ghost variant (`.ui_button_ghost`):** this repo's own invention — the source's `CTAButton` only ships a yellow and a black variant, no white one. Used for a secondary action sitting next to a primary CTA (e.g. "Visit bina" + "See the family survey"). Shares `.ui_button`'s exact shape/sizing/weight for one consistent button family; only the color scheme differs — white background, black text, hover grass, active mint.

**Arrow icon — nav only.** The source component can render a trailing `→` arrow (`showArrow`, on by default) on *any* CTAButton instance. In this repo, **the arrow appears only on the top nav CTA** (`BaseLayout.astro`) — every other `.ui_button`/`.ui_button_ghost` use, anywhere on any page, is text-only, no arrow icon and no literal `→`/`←` character appended to the label. The one exception is a genuine back-navigation control in a multi-step form (e.g. `/book-adventure`'s "← Back") — that's a directional/functional glyph for reversing a step, not a decorative CTA arrow, and Rule 8 below (underline-as-decoration) doesn't reach it either since it isn't a link. Nav arrow SVG: `viewBox="0 0 20 20"`, path `M4 10H16M16 10L11 5M16 10L11 15`, `stroke="currentColor"` `stroke-width="2"` round caps/joins, sized `clamp(0.75rem, 1.04vw, 1.69rem)` — copied exactly from the source's own arrow icon.

**Dual-CTA sections — primary right, secondary left and outlined.** Applies whenever a section (or card) offers two calls-to-action side by side toward different destinations (e.g. `/reviews`' closing "Visit bina" + "See the family survey", `/esa/[state]`'s hero "Start your bina journey" + "See every step for {state}", `/esa`'s JS-rendered results card "Visit bina to start" + "{state} program site"/"Email us about funding") — not a wizard's forward/back step controls (`/book-adventure`'s "Continue"/"← Back" is a different pattern — reversing a step, not offering an alternative destination — and keeps its existing order and styling).
- **Primary** (the main action) is the unmodified `.ui_button` — accent-fill unchanged, no arrow (still nav-only, per the rule above) — positioned **on the right**.
- **Secondary** is positioned **on the left**, and is outlined, not solid-filled: transparent background, `2px` border, matching text color — never white/solid-filled, never a fixed black/white scheme *chosen arbitrarily*. Built from `.ui_button_ghost`'s shape/sizing (same class, for the fluid clamp() spacing and font) with its colors overridden per-instance via `!` utilities — `.ui_button_ghost`'s own default (white fill, black text) stays as the fallback for secondary actions *outside* this dual-CTA pattern (like `/book-adventure`'s "← Back"), so the global class itself is untouched.
- **On a dark-bg section**, the outline/text color is the section's own accent (whatever its heading/body text already uses — same lookup as Rule 9's active-tab rule): `!border-bina-grass !bg-transparent !text-bina-grass`, etc. `/reviews`' closing section is `text-bina-grass` throughout, so its secondary CTA is grass; `/esa/[state]`'s hero is `text-bina-purple`, so its secondary CTA is purple; `/esa`'s JS-rendered results panel is a `bg-coal-black` card (Rule 12 — no border) with purple/lila as its one accent, so its secondary CTA (`"{state} program site"` / `"Email us about funding"`) is purple too, per this same dark-bg case, not the accent-card case below. Hover/active fills in with that same accent color and switches text/border to black (`hover:!bg-bina-grass hover:!text-coal-black hover:!border-coal-black`) — the same "outline fills solid on interaction, text goes black" convention as Rule 9's tab/select hover states.
- **On an already accent-filled card** (transparent/dark-fill dual-CTA panels like `/esa`'s take the dark-bg case above instead — this case is for a CTA pair sitting directly on a solid accent-colored card fill, e.g. inside a `bg-bina-*` stat card), an accent-colored outline would be invisible against the matching fill — Rule 2's "always black on an accent card" convention governs instead: `!border-coal-black !bg-transparent !text-coal-black`. Hover/active inverts by filling solid black with the *card's* own accent as the text color (`hover:!bg-coal-black hover:!text-{accent} hover:!border-coal-black`) — same "fills solid on interaction" spirit, just black-first since the card itself already supplies the accent.
- **Markup order should match visual order** — write the secondary CTA first in the DOM, followed by the primary, inside the same `flex` row (not a CSS `order` override) so keyboard/reading order matches what's on screen left-to-right.

### `ui_link.astro` — the standard hyperlink component

**The one reusable hyperlink component sitewide — replaces every hand-coded `<a class="underline …">`.** Before this component existed, every page hand-rolled its own link classes with no shared spec, so hover behavior was inconsistent (most links had none at all) and underline offset/thickness varied page to page. Extracted from thebinaschool.com's own blog article template (`Bina-School-R-D/website`, `.blog-rich-text a` / `.blog-rich-text a:hover` in `src/styles/index.css`) — re-extract from there if the source's link styling changes.

**🔴 Hand-coded `<a>` tags are not permitted anywhere a plain text hyperlink is being rendered — including inside shared components, not just page files.** This is stated explicitly because it was violated in practice: the original sitewide link-migration task (see Step 4 in the git history of this file) audited and converted every hand-coded link in the six `src/pages/*.astro` files, but never checked `src/components/sections/*.astro` — so `card_testimonial.astro` kept two hand-coded `<a>` tags (its source-attribution link in the compact card view, and the matching link inside its "See more" dialog) that were never touched. Both looked identical to real `<UiLink>` output at a glance (same underline, same color) but had **zero hover or focus-visible CSS at all** — a real, live bug on `/reviews` (every card in the wall) that went undetected because the audit method (grep the page files) structurally couldn't see into component internals. **The lesson, not just the fix:** any future check for "did every link get migrated" must grep `src/components/**/*.astro` as well as `src/pages/**/*.astro` — a page importing a component is not evidence the component's own markup was audited.

**Legitimate exceptions to "every `<a>` must be `<UiLink>`" — this rule is about plain text hyperlinks specifically, not every element that happens to render as `<a>`:**
- **`.ui_button` / `.ui_button_ghost` buttons** (see "Standard CTA button" above) — a completely different, already-specified UI pattern: filled/outlined chunky buttons, never underlined, with their own background-color hover transition instead of an opacity fade. Every CTA button sitewide (`Visit bina`, `Start your bina journey`, `card_prompt`'s primary button, etc.) stays exactly as it is — folding these into `ui_link` would mean discarding an entire, correct, separately-documented button spec for no reason.
- **`pill_source.astro`** — a deliberately different, non-underlined outlined badge with its own bespoke hover (border/background/text-color shift, not an opacity fade) — see that component's own doc comment: it's explicitly "outside the 8-accent design system," styled in neutral grays so it never competes with a nearby CTA button. Not a text link in `ui_link`'s sense.
- **`BaseLayout.astro`'s nav logo** (`<a href="https://thebinaschool.com" aria-label="bina — home">`) — the persistent brand mark, no visible text content at all (an image/wordmark), not a hyperlink `ui_link` was built to style.
- **`/esa.astro`'s JS-rendered results panel** — the one genuine *technical* exception, not a stylistic one: this panel is built by concatenating raw HTML strings and injecting them client-side via `.innerHTML` inside a `<script>` tag, so it structurally cannot render an Astro component (`<UiLink>` only exists at Astro's build/render step, never at runtime in the browser). These links instead hand-match `ui_link`'s exact resolved output classes — see the note below on where the shared `.ui_link` CSS lives, which is exactly what makes this hand-matching approach work at all.
- **`layout_footer_complete.astro`'s nav-column links** — explicitly documented as a literal, faithful port of thebinaschool.com's own footer styling (mint text, no underline, `hover:opacity-80`) rather than a redesign — see that component's own catalog entry. Not wired into any page yet, so not a live instance of anything, but flagged here so it isn't mistaken for an oversight if it ever is adopted.

**Where the hover/focus CSS actually lives, and why it has to live there.** `ui_link.astro`'s own `<a>` carries two kinds of classes: plain Tailwind utilities (`underline`, `decoration-2`, `hover:opacity-70`, `transition-opacity`, `focus-visible:outline-2`, etc.) and one custom class, `.ui_link`, for the one thing Tailwind utilities can't express (`outline-color: currentColor`). The Tailwind utilities are **global by construction** — Tailwind scans every `.astro` file's raw source text (including inside `<script>` blocks and JS string literals, not just JSX-style attributes) and generates one shared stylesheet with those classes in it; any element anywhere in the build that carries `hover:opacity-70` gets that rule, regardless of whether it came from `<UiLink>`, from a hand-matched string in `esa.astro`'s client script, or from anywhere else. The custom `.ui_link` class is different: it started as a **component-scoped** `<style>` block inside `ui_link.astro` — which Astro compiles by rewriting the selector with a hashed `data-astro-cid-*` attribute, so the rule would only ever match markup Astro itself rendered *through that component*. That silently broke the one exception above (`esa.astro`'s client-injected raw HTML never carries that hash attribute), so `.ui_link` was moved out of `ui_link.astro`'s scoped `<style>` into a plain, global rule in **`src/styles/global.css`'s `@layer components`** (alongside `.ui_button`, `.card_base`, `.ui_input`, etc.) — see that file for the exact rule. **Any future custom CSS this component needs (not expressible as a Tailwind utility) belongs in that same `@layer components` block in `global.css`, never in a `<style>` tag inside `ui_link.astro` itself** — a scoped style is invisible to the one case (`esa.astro`) that can't use the component directly, and would silently reintroduce the exact class of bug this fix closed.

**Underline is the one permitted use of underline sitewide.** Rule 8 below bans decorative underline everywhere else (a headline word, emphasized body copy, any non-link element) — a `<UiLink>` is the sole exception, because per standard web convention underline is reserved specifically as a hyperlink signal. Every `<UiLink>` instance keeps its underline in both resting and hover states; nothing about hover removes it.

**Props:** `href` (string), `variant?: 'inline' | 'standalone'` (default `'inline'`), `cardFill?: 'accent' | 'dark'` (default `'dark'`), `accentColor?` (one of the 7 non-yellow accents — required when `cardFill="dark"`), `arrow?: boolean` (standalone only — inline links never show an arrow regardless of this prop), plus a passthrough `class`.

**Two usage variants:**
- **`variant="inline"` (default)** — a link sitting mid-sentence inside a paragraph of body copy. Size inherits from the surrounding text (no `text-*` token of its own) so it sits naturally at whatever size that sentence already is. Weight 600 (semibold), matching the source exactly. **Never shows an arrow**, even if `arrow={true}` is passed — an arrow mid-sentence reads as a typo, not emphasis.
- **`variant="standalone"`** — an emphasis link on its own, e.g. "Book a call with bina →", "See the family survey →". Sized `text-body-3` (18px, Rule 10's link/button-text tier) and weight 700 (bold) — bolder than the inline case on purpose, matching this repo's pre-existing hand-coded standalone links this component replaces. Shows an arrow by default; pass `arrow={false}` to suppress it for a specific instance that genuinely shouldn't have one.

**Three background cases (Rule 2 / Rule 14 — the same `cardFill`/`accentColor` prop pair every other section component uses):**
- **`cardFill="dark"` (default)** — for the `#1c1c1c` page background OR a `#000000` black card. Both resolve to the same color logic (the section's own `accentColor`, Rule 1/Rule 14), so they share one mode rather than needing three separate variants for what is, color-wise, only two cases. Requires `accentColor`.
- **`cardFill="accent"`** — for a link sitting on a card filled with a solid accent color. Color is `#000000` (Rule 2 — text on an accent-filled card is always black); `accentColor` is not read in this mode.

**Resting spec:** `color` per the case above, `font-weight` 600 (inline) / 700 (standalone), `text-decoration: underline`, `text-underline-offset: 2px`, `text-decoration-thickness: 2px` (this repo's own pre-existing convention from `/esa`'s hand-coded standalone links — the source specifies no thickness at all). Underline-offset and the hover transition are adopted from the source's own sibling `.legal-rich-text a` rule, not `.blog-rich-text a` itself — the blog rule has neither (an instant-snap hover, no offset), which reads as an oversight in the source's own two nearly-identical rules disagreeing with each other, not a deliberate blog-specific choice.

**Hover spec:** `opacity: 0.7`, `transition: opacity 0.2s ease` — the source's own values, kept exactly, no color swap. **This is the one part of Step 2 that needed a deliberate check, not an assumption**: the source's own blog page background is itself dark, so the opacity fade was already engineered against a dark context — it was verified (via real mouse-hover testing, not just reasoning) to stay legible in all three of this repo's background cases, including on a solid accent-filled card, so no adaptation of the hover mechanic itself was required. Only the *resting* color needed to vary per case, and that requirement came from Rule 2/Rule 14 independent of hover.

**Focus-visible spec:** `outline: 2px solid currentColor`, `outline-offset: 2px`. **The source declares no focus-visible state at all** (falls through to the browser default outline) — a real accessibility gap, not a deliberate absence, on a component every keyboard user will tab through. Closed here, modeled on this repo's existing `.ui_input` focus-visible precedent (that one uses a fixed pink at a heavier weight for a large form field; this uses a lighter 2px in the link's own resolved color, appropriate for inline text).

**Visited state:** none, matching the source exactly.

**Arrow direction is derived from `href` automatically, never chosen manually** — `→` for an internal bina destination (a relative path starting `/`, or this site's own `https://go.bina.school` origin), `↗` for anything external (another domain, `mailto:`, `tel:`), matching the sitewide convention already established by `/esa`'s hand-coded links before this component existed. External links also automatically get `target="_blank" rel="noopener"` — matching the source's own `ArticleBody.tsx`, which applies the same external-link `target="_blank"` as a post-render DOM pass; done here at build time instead, since Astro doesn't need a runtime pass for a static `href`.

- **Rule 8 — underline is a hyperlink signal, never a decorative one. Applies site-wide, light and dark palette alike, not just this section's dark-background cards.** Underline styling (`underline`, `decoration-*`, `underline-offset-*`) may only appear on an actual `<a href="…">` — a real, clickable link — per standard web convention. It must never be used as a standalone visual accent on non-link text: not a headline word, not emphasized body copy, not any other decorative treatment. This reverses an earlier pattern (`<span class="underline decoration-bina-yellow decoration-8 underline-offset-4">`) used to highlight one word inside a hero `<h1>` on `/book-adventure`, `/family-survey`, `/reviews`, and `/student-results` — that word is now plain text like the rest of the heading, no special color or weight treatment. **`ui_link.astro` (see its own section above) is the one sitewide instance where underline is correct** — it's an actual `<a href>`, exactly the case this rule carves out.
- **Rule 9 — tab/selector buttons and dropdown/select fields never use a solid white fill in their default (unselected) state.** Applies to any toggleable UI chip — tabs, pill selectors, radio-style button groups — and to `<select>`/dropdown fields. The unselected state is **outlined only, no background fill**: a 2px border and matching text color, no `bg-white`. The selected/active state is unaffected by this rule and keeps its existing highlighted treatment (e.g. solid `bg-coal-black` fill with colored text).
  - **On an accent-colored card background** (e.g. `bg-bina-orange`, `bg-bina-pink`): outline and text are `#000000` (`border-coal-black text-coal-black`) — same as every other black-bordered element on an accent card (Rule 2's spirit). Example: `/student-results`' age/level tabs, sitting directly on the orange results card.
  - **On a dark background** (`#000000`/`bg-coal-black` or `#1c1c1c`/`bg-dark-bg`): a black outline is invisible, so outline **and** text instead match the accent color already used by that same control's selected/active state — never plain black, never white. Example: `/book-adventure`'s step-progress pills and age-group buttons sit directly on `bg-dark-bg`/`bg-coal-black` and their active state is `bg-coal-black` fill with `text-bina-grass` — so their unselected state is `border-bina-grass text-bina-grass`, not black. This was a deliberate correction: a first pass used literal black-on-black here per a too-literal reading of this rule, which was invisible against the page background before the accent-matching case was added.
  - **Which case applies is decided by the control's own immediate background, not the wider page.** Most controls sit directly on their surrounding card/page fill with no fill of their own (the two examples above), so "immediate background" and "surrounding card/page" are the same thing. `ui_dropdown.astro` (below) is the one exception worth calling out explicitly: it's deliberately given its own solid dark fill (`#000000`) rather than sitting transparently on whatever accent card contains it, so *its* immediate background is dark even when the card around it is an accent color (e.g. `/esa`'s lila state-tool card) — meaning it always takes the dark-background case (outline + text = the section's accent, `bina-purple` there), never the accent-card case, regardless of what color card it's dropped into.
  - **Native `<select>` elements cannot be brought into this rule with CSS alone — rebuild as `ui_dropdown.astro`.** A native select's closed-state box can be restyled (background, border, text), but its *open* option-list popup is rendered by the browser/OS, entirely outside CSS's reach — no override gets a native select's open dropdown a dark fill and an accent border. This was caught on `/esa`'s state picker: its closed box had apparently been restyled already, but the code still read `bg-white` — the earlier Rule 9 sweep had wrongly logged it as already-compliant without the fix actually landing. Any `<select>` on any page must be rebuilt with `ui_dropdown.astro`, not CSS-patched.
  - **Any icon/arrow glyph inside a tab, selector, or dropdown — a chevron, caret, checkmark, whatever — takes the same accent color as that control's own border/text, always.** It is never left at a default/inherited color. On `ui_dropdown.astro`, the chevron SVG uses `stroke="currentColor"`, which only resolves to the accent if `color` is set on an ancestor the SVG actually inherits from — setting it on a text label span next to the icon, instead of on the shared container both sit inside, silently leaves the icon on the browser's inherited default (a real bug caught on `/esa`'s state picker: the label read correct `bina-pink` while the chevron stayed a default gray). Set `color` on the control's own root/trigger element, not on a child text node, so every descendant relying on `currentColor` — icons included — resolves it the same way.
  - Hover states are unaffected by this rule (e.g. `hover:bg-bina-yellow` on an unselected tab is still fine) — only the *default, unselected, non-hover* fill is in scope. When a hover fill is an accent color, its text/border should still switch to black to stay Rule-2-compliant (e.g. `/book-adventure`'s age buttons: `hover:border-coal-black hover:bg-bina-yellow hover:text-coal-black`).
  - **The selected/active tab's text color must match the section's accent color — the same color used elsewhere in that section (card text, headings). Never use an unrelated accent color for the active tab.** Check the section's own heading/body text color (and, if the active tab reveals a result card, that card's own text color) and match it — don't default to a component's previous or "usual" accent without checking. Caught on `/student-results`: the age/level tabs' active state showed `text-bina-grass`, but that section's own heading, body copy, and the black stat card the tab reveals are all `text-bina-orange` — a real mismatch, not a stylistic choice. Fixed to `aria-pressed:text-bina-orange`. `/book-adventure`'s step-progress and age-group tabs were already correct — that page's entire wizard section (headings, labels, body copy) is `text-bina-grass` throughout, so their active `text-bina-grass` already matched.
- **Rule 25 — a button's label alignment follows the button's own width, not Rule 13's section-alignment rule.** Two patterns coexist and both are correct, most visibly side by side in the testimonial grid:
  - **Full-width buttons center their label.** When a button spans the full content width of its card/container (`w-full`), there is no competing left edge left in the button's own box for the label to align against — centering reads as the button's own internal balance, not a section-alignment choice. Reference: `card_prompt`'s primary `.ui_button` (`w-full text-center`) — see that component's own entry.
  - **Content-width buttons align left with the text above them.** When a button is sized to its own label rather than stretched (e.g. `self-start` inside a flex column), it reads as a continuation of the text column above it, so it stays flush with that column's left edge rather than centering inside space it was never given in the first place. Reference: `card_testimonial`'s "See more…" button (`self-start`, sized to its label) — see that component's own entry.
  - **This does not conflict with Rule 13.** Rule 13 governs how a *section's* containers and text align relative to each other (left by default, centered only for a closing/decision moment) — it decides whether a button, as a block, sits left-anchored or spans full width in the first place. This rule governs a narrower, later question: once a button has that width, where does the *label* sit *inside* it. A full-width button is not "a section going centered" — it's one button, already placed by Rule 13 or by its container's own layout, choosing the only sensible label position for a box with no remaining left edge to align to. Don't read a centered button label as a Rule 13 violation, and don't "fix" a content-width button's left-aligned label to centered (or vice versa) without checking which case actually applies first.

## 🔴 Decorative & brand elements

### Brand rule

The company name is always lowercase: `bina`, `bina school`, `thebinaschool.com`, `hello@thebinaschool.com`. Ages are **4–15**. Scan every page for capitalized `Bina` before shipping.

### `deco_layer.astro` — opt-in, per page

Small margin illustrations (a leaf, a lily pad, a bird) that stay fixed in the viewport for a page's entire scroll — extracted from thebinaschool.com's own decoration pattern (`Bina-School-R-D/website`: the admissions page's palm leaves, the open-house page's lily pads + heron). Rendered **once per page, centrally, by `BaseLayout`** via its own `decorationSet` prop — pages don't import or place `<deco_layer>` themselves. Earlier versions of this were section-scoped (`position: absolute`, dropped inside one hero) — that model is gone; see the "position: fixed, and why every section needs a matching change" note below for why going page-wide required more than swapping one CSS property.

**Opt-in, never automatic.** No page gets a decoration unless `decorationSet` is explicitly passed to its `<BaseLayout>` call.

**Overlap rule — decided, not a trade-off to reconsider:** decorations MAY overlap cards, tables, charts, and any dense section. There is no "don't place behind dense content" restriction, no fading, and no per-section visibility control. Decorations always render **behind** real content — content always wins wherever the two occupy the same space — so nothing is ever obscured; overlap is fine because the stacking guarantees it's harmless.

**Which set goes on which page is assigned spontaneously — there's no rule mapping a set's theme to a page's content**, and no need to invent one. `deco_leaves` on `/family-survey` doesn't mean anything about family surveys; `deco_waterlily` on `/student-results` doesn't mean anything about test results. When generating or updating a page, either pick whichever set isn't already used on the page right before/after it (so two adjacent pages don't feel identical), or just alternate. Current assignment:

| Page | Set |
|---|---|
| `/reviews` | `deco_leaves` |
| `/esa` | `deco_waterlily` |
| `/esa/[state]` | `deco_leaves` |
| `/student-results` | `deco_waterlily` |
| `/family-survey` | `deco_leaves` |
| `/book-adventure` | `deco_waterlily` |

**Usage — one prop on `BaseLayout`, nothing else in the page's own markup:**
```astro
<BaseLayout title="..." description="..." decorationSet="deco_leaves">
  ...
</BaseLayout>
```
**Props on `deco_layer` itself** (only relevant if calling it directly, which no page does): `set`, `left?`/`right?` (booleans, default both `true`), plus passthrough `class`.

**`position: fixed`, and why every section needs a matching change.** This is the single trickiest part of this component — worth understanding in full before touching any of the three files involved (`deco_layer.astro`, `BaseLayout.astro`, or a page's own section markup), because two plausible-looking approaches were tried, verified empirically (a throwaway HTML test page, not just reasoned through), and rejected:
- **`z-index: 0` alone** paints the decoration ABOVE ordinary non-positioned content (headings, cards, text) — CSS stacking rules put non-positioned in-flow content in a lower paint layer than any positioned element with `z-index: 0`/`auto`, regardless of DOM order. A bare `z-index: 0` fixed decoration sits on top of every card on the page.
- **Promoting `<main>` itself** (`class="relative z-[1]"`) fixes that, but breaks the other half of the requirement: it lifts every section's own *background* along with its content as one unit, so the decoration becomes invisible against every section too — there's no gap in the page for it to ever show through. In practice this shipped once and made every decoration disappear on every page, at every screen size — a real bug, not a trade-off.

**The fix that actually works:** the decoration itself stays `z-index: 0`; `<main>` is left deliberately unpromoted; and **every section's own inner content wrapper** — the `mx-auto max-w-6xl px-8 …` (or `max-w-4xl`/`max-w-2xl`) div every section already has, per this repo's standard-container convention — gets `class="relative z-[1]"` added to it, while the `<section>`/`<header>` element carrying the actual background color stays untouched. That split (background layer stays put, content wrapper lifts) is what lets a decoration paint above a plain section background but below that section's real content, consistently, on every section of the page — not just the one it happens to start in. This was applied to **every** section on all six pages using decorations (including inside the shared `layout_stat_section.astro`, which needed the same one-line fix since three of the six pages route their sections through it) — see the page-by-page notes in the pages table for exactly which wrapper divs were touched. **Any new section added to a page that already has a `decorationSet`, or any new page that adds one, needs this too** — it isn't automatic, and forgetting it either lets the decoration cover real content (no promotion at all) or makes it vanish behind that section's background (promoting the section instead of its inner wrapper).

**Footer stop — `IntersectionObserver`, not a hardcoded scroll offset.** Decorations must never appear over or behind the footer. `BaseLayout`'s own `<footer>` carries a `data-site-footer` attribute; `deco_layer`' own script does `new IntersectionObserver(...).observe(document.querySelector('[data-site-footer]'))` and toggles a `side-decoration-past-footer` class on both images whenever the footer's intersection state flips. That class sets `display: none`, and wins over the breakpoint's `display: block` on plain CSS specificity (two classes beat one) — no `!important` needed. Using the footer's actual intersection instead of a fixed pixel value means this is correct for any page length automatically, including future page edits that change how long the page is — a hardcoded number would need re-tuning every time content changes.

**Minimum viewport width: `1280px`** (Tailwind's `xl`, chosen deliberately to match it). This used to be computed as "the width at which the decoration's real opaque pixels clear the 1200px container without touching it" — 1600px, and before an earlier correction, 2560px — but that constraint no longer applies now that overlap is explicitly allowed (content always wins regardless of what's underneath it). The breakpoint's only remaining job is "don't show on a screen with no real margin at all" (mobile/tablet). At 1280px the gutter outside the 1200px container is only ~40px per side; the images (already at 48% of literal source size — see `decoration-sets.ts`'s own SCALE NOTE) are **not** shrunk further to fit inside that gutter — they're simply allowed to crop at the browser's own viewport edge, which is what `position: fixed` content does naturally. Shrinking further to avoid any cropping was considered and rejected: overlap/cropping is fine per the rule above, and the images already read clearly at 48% scale — shrinking more for a problem that no longer exists would just make them harder to recognize as a leaf/lily/heron.

**Vertical stagger — `left` and `right` should sit close together with a small deliberate offset, never far enough apart that one side of a section reads as empty.** Tune this via `verticalOffset` on each `DecorationImage` in `decoration-sets.ts` — it's a per-decoration config field, not anything hardcoded in `deco_layer.astro` (the component just reads `${verticalEdge}: ${verticalOffset}` off whatever the config gives it). Both shipped sets use `verticalEdge: 'top'` for **both** `left` and `right`, with `verticalOffset` values roughly 10-15 percentage points apart (`18%` / `30%`, a 12pp stagger) — enough to read as a deliberate offset, not so much that one side is out of view while the other is front and center.

This corrects a real, confirmed bug, not a style preference: the values both sets originally shipped with were carried over from `verticalOffset`'s doc comment guidance ("copied verbatim from the source's own settled desktop state") — but the *source* positions these images with `position: absolute` inside one specific section, while `deco_layer` is `position: fixed` (viewport-relative, page-wide). Under `position: fixed`, source values that mixed `top`- and `bottom`-anchoring within one set (`deco_leaves`: left `top: 18%`, right `bottom: 8%`) put the two sides at wildly different points on screen — confirmed on `/family-survey`: the left leaf sat near the top of the viewport while the right leaf sat far enough down to be effectively out of view alongside the hero. `deco_waterlily`'s original values (`bottom: -30rem` / `-38rem`, both sides) were worse: both images landed entirely below the viewport at any normal screen height, not just far apart — confirmed as a total-invisibility bug on every page using that set (`/esa`, `/book-adventure`, `/student-results` all showed zero decoration). **Verbatim source fidelity for `verticalOffset` was already wrong the moment this component became page-wide `position: fixed`** — matching source values only ever made sense for the old section-scoped `position: absolute` model. Don't re-introduce mixed-edge or large-magnitude offsets by "restoring" the original source numbers.

### Adding new decoration imagery

No component code changes needed — this is a config + asset-drop workflow, meant to be followable by anyone on the team:

1. **Drop the image file** into `src/assets/decorations/` (flat folder, no subfolders — the component finds it by filename via a glob, regardless of which set it belongs to). Keep the original format and resolution; don't pre-resize — Astro's build pipeline optimizes it automatically.
2. **Add one entry** to `decorationSets` in `src/components/decorations/decoration-sets.ts`, naming the set (or adding to an existing one) and specifying which side, width, and offsets. **Name new sets `deco_<name>`** — lowercase, underscore-separated, describing the imagery itself (`deco_flowers`, `deco_ocean`), not the page it came from or was first used on — that keeps the name stable even if the set gets reused somewhere thematically unrelated (see "assigned spontaneously," above). Real example, copy-pasteable — this is the actual current `deco_leaves.left` entry, already scaled to the shared `0.48` factor (see the breakpoint note above — **if your new image is sized at the literal 1:1 source extraction instead, don't copy the numbers below verbatim**, they won't mean what they look like they mean):
   ```ts
   deco_leaves: {
     description: 'Palm/fern leaves flanking a section, extracted from thebinaschool.com/admissions. Scaled to 48% of source size.',
     left: {
       file: 'palm-leaf-left.png',
       side: 'left',
       verticalEdge: 'top',
       verticalOffset: '18%',
       horizontalOffset: '-2.4%',
       width: '12%',
       maxWidth: 'clamp(8.4rem, 11.11vw, 18rem)',
     },
     // right: { ... } — optional, same shape, omit if this set only decorates one side
   },
   ```
   Field notes — use the exact unit the source site uses (`%`, `vw`, `rem` — never convert to `px`):
   - `verticalEdge` — `'top'` or `'bottom'`, whichever edge the source anchors that image from (they're not always the same edge, even for two images in one set).
   - `verticalOffset` / `horizontalOffset` — the literal CSS value, as a string, for that edge. **`verticalOffset` is NOT the source value** — copying it verbatim was the mistake that caused a real bug once this component became page-wide `position: fixed` (see the Vertical stagger note above). Use `verticalEdge: 'top'` for both `left` and `right` unless there's a specific reason not to, and pick `verticalOffset` values roughly 10-15 percentage points apart from each other, both keeping the images comfortably inside a normal viewport height — not the source's own numbers. `horizontalOffset` should be pre-scaled the same way `width` is (see below) — that part IS still source-derived, just scaled.
   - `width` — CSS width, same string-with-unit rule. Pre-scale it (along with `horizontalOffset`, `maxWidth`, and `height`) by whatever factor keeps the image a reasonably-sized, still-recognizable illustration — not by any "clears the container" math, since overlap with content is fine (see the overlap rule above); the only thing scale needs to protect against now is the image being so large it reads as an abstract color field rather than a leaf/lily/heron once it's cropped at a 1280px viewport edge.
   - `maxWidth` (optional) — only needed if the source caps a fluid `%`/`vw` width with a `clamp()` ceiling so it doesn't grow unbounded on very wide screens.
   - `height` + `objectPosition` (optional pair) — only needed when the image sits inside a box whose aspect ratio doesn't match the image's own natural ratio (an `object-fit: contain` situation) — e.g. `height: '54.40vw'`, `objectPosition: 'left center'`. Omit both when the image just fills its box at natural aspect ratio (`width` + auto height).
3. **Reference the set name** via `decorationSet` on whichever page's `<BaseLayout>` call needs it: `decorationSet="deco_leaves"`. There's no cap on how many sets can exist — `decorationSets` is a plain object, so `deco_leaves` and `deco_waterlily` are the first two entries, not the only two it's designed for. **Also add `class="relative z-[1]"` to every section's own content wrapper on that page** if it doesn't already have it — see the stacking-order note above; this is the one step that's easy to forget since it isn't inside `decoration-sets.ts` or `deco_layer.astro` at all.

**If your new image is sized close to the two existing sets, the shared `0.48` scale factor should already work fine at the `1280px` breakpoint** — just scale your new source numbers by `0.48` the same way before typing them in. **If it's meaningfully bigger or smaller**, judge it visually at 1280px and 1440px rather than reusing `0.48` blindly — the target is "still reads clearly as its own illustration, cropped at the viewport edge is fine." There's no "must clear the container" constraint to solve for anymore (that was the first version's mistake, corrected once already — see the breakpoint note above); don't reintroduce it when sizing a new set.

If a new image needs a field not listed above, add it to the `DecorationImage` interface in `decoration-sets.ts` (with a comment explaining why, same as the existing fields) rather than working around the schema with a one-off hack in the component.

## 🔴 Page philosophy — tools, not essays

Pages are **interactive tools for families**, not long SEO pages. Short, task-focused, multi-step. The reader should feel they're doing a smooth process **with bina** — some steps just happen to occur on state/official websites. Plain language only: no jargon a newcomer wouldn't know ("universal eligibility", "award disbursement" → say who can apply, when money arrives). Assume the reader won't study any official website themselves.

## 🔴 Audience rule — every page is built for three readers at once

Every family-facing page must work for all three of these, at the same time. Assume the reader is one of them and never make the other two pay for it.

| Reader | What they consume | What they must leave with |
|---|---|---|
| **Scanners** | The hero, 4–5 big numbers, and the section headings. Nothing else. | "This is a great school." Never a feeling that they missed the real point by not reading on. |
| **Focused** | The above plus 2–3 lines under each heading. | The same belief, plus the reasoning behind it. |
| **OCDers** | Every word, every expander, every source link, every footnote. | Total confidence that nothing is overstated. One loose claim loses them, and they're the ones who convert hardest. |

**How that translates into markup:**

- **Every heading and big-number label is a complete claim that stands alone.** A metric label is a failure. Write "Parents would send their friends here" (9.42), not "out of 10 on 'would you recommend'". Test: extract all `<h1>`/`<h2>`s and the tile headings into a flat list — it should read as a coherent argument on its own. If a number needs the paragraph beneath it to mean anything, the heading is wrong.
- **Nothing essential below line 3 of any section.** Focused readers stop there. If a fact matters, it's in the heading or the first two lines.
- **Detail goes in `<details>` expanders, figure captions, and the methodology section** — never in the main flow where it taxes the other two readers. Charts, correlation tables, per-option breakdowns and source caveats all belong there.
- **Volunteer the caveat rather than hiding it.** Publishing our weakest score, the response rate, and the limits of a cited benchmark reads as more confident than omitting them, and it's the only thing that holds an OCDer.

**The dual goal — both, or the page has failed:**

1. **Believe this is a great school** — needs proof numbers: satisfaction, recommendation, outcomes, independent benchmarks.
2. **Picture themselves inside it** — needs projection content: second-person copy ("your week as a bina parent"), families like theirs, what a normal Tuesday looks like.

**Sort your stats by which goal they serve, and never let a projection stat open the page.** A projection stat describes who our families *are*; it says nothing about whether we're any good. `/family-survey` originally opened on "70% of our families have a child who doesn't fit a standard classroom" — true, and useless as proof, because a terrible school would report the same 70%. It only works chained to a quality number ("…and those are the families rating us 9.48 out of 10"). Lead with proof; use projection to make it personal.

## Reusable components — `src/components/sections/`

Shared section components live here, not copy-pasted per page. ### How to name a new component

Every component file is `snake_case`, lowercase, with a prefix that tells you what kind of thing it is before you open the file. When adding a new one, don't guess — pick the prefix whose definition actually matches what the thing IS, not where you happen to be using it first (a component built for `/esa` that turns out to be generically useful shouldn't carry `esa_` or reference that page in its name).

| Prefix | For | Ask yourself |
|---|---|---|
| `chart_` | Data-visualization components — anything rendering a graphical or tabular representation of numbers | Does this draw a chart, graph, or data table? |
| `card_` | A single repeatable unit meant to be dropped into a grid or column the *calling page* composes | Is this ONE reusable card, with the page building the grid/columns around it? |
| `section_` | A component that owns its *own* internal composition AND has real behavior beyond a static wrapper (tabs, a whole grid convention, client-side state) | Does this compose more than one piece internally, with actual interactive logic? |
| `layout_` | A structural wrapper with no interactive behavior of its own — a shell, a footer, a static numbered-step set | Is this just a shape/wrapper around content the caller supplies, with nothing to click? |
| `ui_` | A real interactive control — something a reader operates (a link, a dropdown, an accordion, a stepper, a button) | Does a reader click, toggle, or navigate through this? |
| `pill_` | A pill/badge-shaped label or tag — not clickable-as-a-control, not a card | Is this a small rounded label or credential tag, not a card and not a control? |
| `deco_` | Purely decorative, non-informational visual elements (illustrations, margin art) | Does removing this change zero information on the page? |
| `template_` | A whole-page behavioral pattern (a payload contract, a multi-step flow spanning the entire page) — not a single visual section | Does this span the whole page's behavior, not just one section's markup? |

**Variants use a suffix on the base name, never a new unrelated name** — e.g. a hypothetical scored variant of `card_stat.astro` would be `card_stat_score.astro`, not `card_score.astro`. This keeps every variant of a thing alphabetically and visually grouped with its base.

**No abbreviations unless they're already standard in this repo's own vocabulary** (`ui`, `deco` are established; don't invent new ones like `tbl_` for "table" when `chart_table.astro` already reads clearly).

**Component file names are `snake_case`, but Astro/JSX still requires the imported binding used in markup to start with a capital letter** — a tag starting with a lowercase letter is treated as a literal HTML element, not a component reference. So `card_stat.astro` is imported as `import CardStat from '.../card_stat.astro'` and used as `<CardStat />` — the PascalCase import alias is a mechanical, 1:1 derivation from the file name (strip underscores, capitalize each word), never an independent name choice. When adding a component, pick the snake_case file name first per the table above, then derive the import alias from it — don't design the two separately.

CSS-class-only patterns (`global.css`'s `@layer components` — not separate files) follow the same prefix system: `.ui_button`, `.ui_button_ghost`, `.ui_input`, `.card_base`, `.pill_solid`.

## Campaign lead-gen pages — `template_campaign_leadgen`

Ad-hoc lead-gen campaign forms (Tally replacements) are a **standard page type**, not one-offs — named `template_campaign_leadgen` in the naming system above (a `template_`, not a `section_`: this spans a whole page's behavior, including the server-side webhook contract below, not just one visual composition). `/book-adventure` is the reference implementation. Every new campaign page follows it:

1. Multi-step wizard in one `card_base` (intro → contact → qualify → redirect), plain inline script, no framework island. Form fields use `.ui_input` (defined in `global.css`); access inputs via `form.elements` (`form.name` is the form's own attribute — a real bug otherwise).
2. On final submit, `navigator.sendBeacon` posts the lead to the shared n8n **`[S] A4. Campaign Intake`** webhook (`https://binaschool.app.n8n.cloud/webhook/s-a4-campaign-intake`) as a `text/plain` blob (avoids a CORS preflight; the workflow parses JSON from the raw body), then `location.assign`s the redirect — capture is fire-and-forget and must never block or break the redirect.
3. Payload contract: `{ campaign, submission_id, name, email, phone, child_name, age_group, redirect_url, page_url, referrer, utm_* }`. `campaign` = the page slug; `submission_id` = `${campaign}-${crypto.randomUUID()}` (the workflow's dedupe key). New campaigns reuse the same webhook — a new page needs **zero** n8n changes.
4. Anti-bot: off-screen honeypot input (`website`) — if filled, skip the beacon but still redirect.
5. Contact prefill: `?name=&email=&phone=` URL params pre-fill and skip the contact step (parity with Tally hidden fields).
6. Campaign pages are `noindex={true}`.

The receiving workflow lives in `bina-gtm` (`automations/workflows/`) — it writes to Close (note + task, review-flagged lead creation for new emails, no opportunity/nurture) and posts to Slack `#growth-log`. Changing the payload contract means a PR in **both** repos.

## Git workflow

- Branch from `main` → PR → merge. **Never push directly to `main`** (the initial scaffold was the only exception).
- Merging to `main` deploys to GitHub Pages automatically.
- Public marketing pages are indexable by default; sales-enablement/internal pages get `noindex={true}`.

## Content rules

- Factual claims about external programs (ESA amounts, deadlines, regulations) must carry a "verify with the official source" disclaimer and link to the official program.
- **Primary CTA on every family-facing page is `Visit bina` → `https://thebinaschool.com`** (`/esa`, `/student-results` and `/reviews` all do this). We want the main site to take the enquiry; don't invent a page-specific CTA or point at a form unless the page *is* a campaign page. Campaign pages are the exception — `/book-adventure` captures the lead itself, and the paid-search ESA landing pages (`/esa/<state>`) send every CTA to **`https://form.thebinaschool.com/new`** with the label **`Start your bina journey`**, matching the main site's own conversion action (Akis, 2026-08-21). No arrow on this label — per the standard CTA button spec (below), an arrow icon only ever appears on the top nav CTA. `BaseLayout` keeps any `?ref=` from the current URL for 365 days and appends it to every `form.thebinaschool.com` link, mirroring the partner-attribution snippet on the main site (`bina-gtm/notes/partner-program-technical-plan.md` §4); `localStorage` is per-origin, so partner links routed through go.bina.school must carry `?ref=` on the go.bina.school URL itself.
- CTA email is `admissions@thebinaschool.com` — these pages talk to prospective and current families, so email CTAs go to admissions, not the general `hello@` inbox. Main-site links go to `https://thebinaschool.com`.

### Publishing our own data (surveys, results, outcomes)

The OCDer reader is the one we lose permanently if a number is soft, so pages built on bina's own data follow these:

- **Never combine two different surveys or cohorts into one figure.** Label which survey every number came from, on the page itself.
- **Charts get an honest axis.** Bars on a 0–10 rating run the full 0–10; no cropped baselines to inflate a gap. Put the weakest score in the same chart as the best.
- **Disclose the response rate and self-selection bias** in the methodology section, not buried in the footer.
- **Never state a formula you haven't verified.** If a metric's derivation is unconfirmed, use a metric you *can* describe (`/family-survey` swapped an unverifiable FSI 9.5 for overall satisfaction 9.48 — costing 0.02 and closing the hole) rather than shipping a plausible guess.
- **Don't assert what a survey question measured** unless the wording is confirmed. Write copy that holds true either way.
- **No causal claims from correlational data** ("clubs increase retention" when the source attributes it to engagement).
- **Cite external benchmarks precisely, and only for what they actually say.** Include the sample size, link out, and never extrapolate a figure the source doesn't publish.
- **Track unverified claims in an `_openQuestions` array** in the page's JSON so the next session sees them before editing.
- No individual student or family data, ever. Aggregates only, and suppress groups too small to report.
